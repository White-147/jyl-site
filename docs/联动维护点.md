# 联动维护点

本站有几处「同一个事实写在两个地方」的设计。它们本身是必要的（为了首屏性能、无闪烁、静态部署），
但**改动时必须成对修改**，否则会出现难以定位的症状。这份文档把它们集中列出来。

每一条的格式：**联动点 → 涉及文件 → 漂移后的症状 → 怎么改 → 怎么验证**。

---

## 1. 首屏骨架 ↔ 真实 Hero

**为什么存在两份**
`index.html` 里的 `<style id="hero-shell-style">` + `<div id="root">` 内的骨架，
用于消除 JS 加载期的白屏。它必须独立生效，所以不能依赖外部样式表，只能手写一份等价 CSS。

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `index.html` → `<style id="hero-shell-style">` | 骨架样式（手写 CSS） |
| `index.html` → `<div id="root">` 内的 `<section class="hero-shell">` | 骨架 DOM |
| `src/components/Hero.tsx` | 真实 Hero（React） |
| `src/index.css` → `@theme` 的 `--text-*` | 流体字号来源（骨架的 `clamp` 值抄自这里） |

**漂移后的症状**
首屏刷新时文字「跳一下」：位置、宽度或字号在 React 挂载瞬间变化。

**历史故障（实测数据）**
2026-09 修过一次：骨架 H1 写到 `y=104`、真实 Hero 在 `y=188`，挂载瞬间**下移 84px**；
副题块宽度从 1120px 收到 896px（**横向收窄 224px**）。原因是六处盒模型不一致：
内容缺 `max-w-4xl`、内边距写死、`min-height` 用 `62vh` 而非 `100svh - 4rem`、
H1 字号写死 `4.25rem` 而非 `clamp()`、字重写成 900（app 是 400）、
`justify-content` 与 app 的 `sm:justify-center` 不一致。

**当前约定（重要）**
骨架的**内容列 `.hero-col` 设为 `visibility: hidden`**，骨架只负责背景层与光斑。
原因：app 的首项位置 = `0.706 × 容器高度`，而容器高度 = `max(731px, 100svh - 4rem)`。
这是一个随视口高度连续变化的比例，骨架无法用与容器高度同源的度量复现它。已逐一验证并排除：

| 方案 | 实测偏差 |
| --- | --- |
| 固定 px | 640–1500px 视口高度区间内偏差 12–818px |
| 百分比 `padding` | 按**宽度**解析而非高度，偏出 900px 以上 |
| grid `fr` 轨道 | 单行自动放置时轨道塌陷，偏差 56–409px |
| `vh` / `svh` | 生产环境可响应，但无头仿真下不随视口变化，无法回归验证 |

所以**不要再尝试对齐骨架的文字位置**。骨架不渲染前景内容，就没有可错位的东西。

**怎么改**
- 只改 `Hero.tsx` 的视觉样式（颜色、圆角、图标）→ 无需动骨架
- 改 `Hero.tsx` 的**背景层**（光斑位置、网格）→ 同步改 `.hero-shell::before`
- 改首屏文案 → 同步改骨架 DOM（虽然不可见，但改掉更省心；文案也会影响 `subset-fonts` 的字符集）
- 想恢复骨架显示文字 → 必须同时满足：两处盒模型逐项一致 **且** 能接受垂直方向仍有偏差

**怎么验证**

```bash
npm run build && npx vite preview --port 5231
# 逐断点比较「骨架阶段」与「应用稳定后」的 H1 视口坐标
node <诊断脚本> http://localhost:5231/ 1440 900
```

判定标准：`x` 与宽度必须为 0 误差；CLS 必须为 0。

## 2. 首屏内联字体 ↔ 字体子集

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/fonts/*.woff2` | 子集化产物（唯一来源） |
| `scripts/subset-fonts.mjs` | 生成子集 |
| `scripts/inline-firstscreen-fonts.mjs` | 把柳建毛草 + 得意黑 base64 内联进 `index.html` |
| `index.html` → `<style id="font-face-inline">` | 内联产物（勿手改） |
| `vite.config.ts` → `FONT_FILES` | 构建后注入的 `<link rel="preload">` 列表 |

**漂移后的症状**
新增文案的用字不在子集内 → 回退到系统字体，粗细/字形与全站不一致。
或：`index.html` 内联的是旧字体，`src/fonts` 是新的，两者静默不同步。

**历史故障**
内联块原本是**人工粘贴**的、且内联的是子集化之前的旧文件，**没有任何生成器**。
文案变更后重跑子集化，`src/fonts` 更新而 `index.html` 不会。

**怎么改**
改完任何文案后：

```bash
npm run fonts:subset    # = subset-fonts.mjs + inline-firstscreen-fonts.mjs，两步必须成对
```

若新增了**首屏**展示层用字（H1、区块标题），还要看 `vite.config.ts` 的 `FONT_FILES`
是否需要把该字重加入预加载列表。

## 3. 主题初始化 ↔ 主题切换组件

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `index.html` → `<head>` 内联脚本 | 首屏前套用主题，避免闪白/闪黑 |
| `src/hooks/useTheme.tsx` | 主题状态**唯一来源**（Context）+ 同步 `theme-color` + 落盘 |
| `src/components/ThemeToggle.tsx` | 三态下拉（自动 / 浅色 / 深色） |
| `src/components/TopBar.tsx` | 常驻顶栏里的那个实例（**全端、两种视图都有**） |
| `src/components/MobileTabBar.tsx` | 手机端底部 Tab Bar 里的实例 |
| `index.html` → `meta[name="theme-color"]` | 移动端状态栏配色（**只放一个**，由 JS 全权覆写） |

**漂移后的症状**
- 内联脚本与组件判定逻辑不一致 → 首屏闪一下再跳到正确主题
- `localStorage` 的键名或取值集合不一致 → 主题"记不住"
- 画布底色改了但 `theme-color` 没改 → 移动端地址栏与页面脱色
- 主题控件只挂在某个视图上 → **该视图没有主题入口**（2026-09 的实际故障：文档区
  `#/docs/ue5` 里三个浮层都不渲染，用户完全改不了主题）

**当前约定（2026-09 起）**
主题控件由 `TopBar` 提供，而 `TopBar` 是**全端常驻**的（不区分视图与断点），
所以任何新视图都会自动获得主题入口。`MobileTabBar` 里那个实例是历史遗留的第二个入口，
保留但不再是必需项 —— 若将来要精简，删它不会造成功能缺失。

**怎么改**
三处的画布色值必须一致：`src/index.css` 的 `body` 背景、`index.html` 的 `theme-bg-inline`、
`useTheme.tsx` 的 `CANVAS`。键名固定为 `localStorage.theme`，取值集合固定为 `auto | light | dark`。

## 4. 色板 ↔ 组件里硬编码的颜色

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/index.css` → `@theme` | 色板唯一来源 |
| 各组件里的 `rgb(...)` / `#hex` 内联 | 装饰性渐变、光晕、SVG 描边 |

**漂移后的症状**
改了色板，但某些渐变/光晕仍是旧色，页面出现两种色系。

**当前已知的硬编码位置**（改色板时逐个检查；下表已按 2026-09 的石墨 + 琥珀改版更新）

| 位置 | 当前值 |
| --- | --- |
| `About.tsx` 多定位卡背景 | `radial-gradient(... rgb(217 122 6 / 0.14) ... rgb(247 189 110 / 0.16))`（= brand-500 / brand-400） |
| `BackToTop.tsx` 进度环渐变 | `<stop stopColor="#9d5300">` / `"#f7bd6e"`（= brand-700 → brand-400，与导轨液柱同色） |
| `BackToTop.tsx` 阴影 | `rgba(157,83,0,0.28)`（= brand-700） |
| `SideDotsNav.tsx` 管体与节点 | `rgba(157,83,0,…)` 系列、`bg-brand-300`、`rgba(242,169,59,…)` |
| `index.css` 卡片阴影 | `rgb(157 83 0 / 0.06)` |
| `Hero.tsx` 头像 ring | 走 `ring-brand-100`，已是 token ✓ |

> 改主色时**这张表就是检查清单**。历史教训：改色板时漏掉了 `About.tsx` 的光斑与
> `BackToTop.tsx` 的进度环，导致页面上同时存在新旧两种色系的装饰层。

建议做法：把这类装饰色收敛为 `index.css` 里的 `--glow-*` 变量，组件引用变量而非字面量。

## 5. 响应式断点：JS 与 CSS 各写一份

**涉及文件**

| 文件 | 断点 |
| --- | --- |
| `src/hooks/useIsMobile.ts` | `(max-width: 639px)` |
| `src/components/Experience.tsx` | `sm:hidden`（640px 起隐藏） |
| `src/components/Hero.tsx` | `sm:hidden` / `hidden sm:block` |
| Tailwind 默认 | `sm = 640px`、`md = 768px`、`lg = 1024px` |
| `src/index.css` 的 `section-*` / `hero-inner` | `@media (min-width: 640px)` |
| `src/index.css` 的 `.rail-gutter` | `@media (min-width: 768px)`（与右侧导轨出现的 `md` 对齐） |
| `src/index.css` 的 `--breakpoint-xl3: 74.25rem` | 自定义断点 1188px，供 `xl3:` 前缀使用（当前仅剩卡片内边距在用） |
| `src/components/SideDotsNav.tsx` 的 `RAIL_QUERY = '(min-width: 768px)'` | 与 `.rail-gutter`、Tailwind `md` 同一个 768px：桌面导轨的出现/隐藏开关，还控制**是否挂载导轨子树** |
| `src/index.css` 的 `.mobile-flat-bar` | `@media (max-width: 767px)`，与 `md` 互补：窄屏关掉吸顶导航与底部 Tab Bar 的 `backdrop-filter` |

**⚠️ 右侧导轨是「条件挂载」而不是「CSS 隐藏」**
`SideDotsNav` 外层 nav 常驻并带 `hidden md:flex`；内部 `Rail` 只在 `RAIL_QUERY` 命中时挂载
（`useRailVisible`，基于 `useSyncExternalStore`，避免首帧按手机渲染再切桌面）。
改这个断点时**必须同时改 `RAIL_QUERY` 和 className**，否则会出现「CSS 说显示、JS 说没挂载」
或反过来的空白导轨。历史上它是 CSS 隐藏、组件照跑：手机上白背一个 scroll 监听（每帧读
`scrollHeight` 强制布局）+ 两个 ResizeObserver + 一个 MutationObserver，见 README 的性能预算。

**链路卡列数：恒定两列 + 容器上限 1024px（已废除三列方案）**
About 的四张「能力链路卡」每张内部有两组「数字 + 后缀」，可读宽度低于约 320px 时
数字与后缀会被挤成两行、正文每行掉到 16 字以内。历史实测（已计入 md 起的导轨留白与容器 padding）：

| 视口 | 三列时每张宽 | 结论 |
| --- | --- | --- |
| 1024 | 280px | 太小 |
| 1188 | 323px | 刚好够（三卡时代取值） |

三卡时代曾用 `xl3`（1188px）切三列。**2026-09 加到四张卡后该方案废除**：
四张卡在 3 列网格里必然排成 3+1，第四张独自占一整行；平板与 1024–1188px 视口
更早就已经是 2+1 的孤卡（这正是当初被反馈的问题）。
现方案：`<640` 单列 → `≥640` **恒定两列（2×2）**，容器 `sm:max-w-5xl`（1024px）居中。
每张约 480px，数字与后缀同行、正文每行 30 字以上。

**改动卡片内边距、容器上限或 `.rail-gutter` 后，这三个数字（320 / 480 / 1024）需要一起重新验算。**

**漂移后的症状**
640px 附近出现「JS 认为是手机、CSS 认为是桌面」的错配：折叠按钮与布局状态对不上。

**当前状态**
`useIsMobile` 用 `max-width: 639px`，与 Tailwind 的 `sm:hidden`（`min-width: 640px` 才隐藏）
**恰好互补，无缝隙**。改动任一处时保持这个互补关系。

**建议**
能不靠 JS 判断的就不靠：优先用 `hidden sm:block` 这类纯 CSS 方案。
`Experience` 的「移动端默认折叠要点」因为需要交互状态才用了 JS，属合理例外。

## 6. 锚点停靠位 ↔ 滚动侦测线 ↔ 导航点击行为

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/data/scrollTargets.ts` | 偏移量**单一来源**（手机 112px / ≥640px 104px，= TopBar 64 + 间隙） |
| `src/index.css` 的 `.anchor-offset` | 用上面的值生成 `scroll-margin-top`（**普通类 + 显式 @media**，见下方「不要用 @utility」） |
| `src/components/TopBar.tsx` | 常驻顶栏，`h-16`（64px）—— **偏移量的几何来源**，改高度必须同步改上面两处 |
| `src/index.css` 的 `--site-bar-h` / `--rail-top` | 同一高度的变量化来源（导轨起点也用它） |
| 各 `section` 的 `className` | 统一写 `anchor-offset`，不再各写 `scroll-mt-*` |
| `src/hooks/useScrollSpy.ts` | 读取同一组值作为判定线（+2px 容差） |
| `src/hooks/useAnchorScroll.ts` | 导航点击的滚动实现（见下方「为什么不用原生锚点」） |
| `src/data/navigation.ts` | 首屏 `#top` 也登记为节点（`isChapter: false`）；带 `href` 的条目是跨视图跳转 |
| `src/components/SideDotsNav.tsx` | 节点位置 = 「滚到停靠位时的滚动进度」，与液柱同一度量；**只展示页内章节**（带 `href` 的跨视图条目被 `RAIL_SECTIONS` 过滤掉） |
| `src/components/Docs.tsx` | 文档区的 `HEADER_OFFSET` 与 `.doc-content` 的 `scroll-margin-top` 同样按顶栏高度取值 |

**⚠️ 2026-09 改版的口径变化**
以前只有手机端有吸顶浮层（80px），桌面/平板"无浮层"所以取 88px；
现在 `TopBar` **全端常驻 64px**，三端都按「64 + 间隙」算（手机 112 / 桌面 104）。

**⚠️ 不要用 `@utility` + 嵌套 `@media` 实现**
实测 Tailwind v4 的 `@utility` 会**丢掉嵌套的 `@media`**，只生成基础声明：

```css
@utility anchor-offset { scroll-margin-top: 104px; @media (width >= 40rem) { scroll-margin-top: 88px } }
/* 构建产物只有：.anchor-offset{scroll-margin-top:104px}  ← 88px 那条从未生成 */
```

后果是**桌面端一直在用手机端的 104px**，且因为 `useAnchorScroll` 的「停稳后纠正」机制会把落点补正，
这个错误被掩盖了很久没被发现。同类问题也发生在 `rail-gutter` 上。
现在两者都写成**普通类 + 显式 `@media`**（放在 `@import "tailwindcss"` 之后即可，优先级够）。
自检方法：`npm run build` 后 grep 构建产物，确认两条 media 查询都在。

**漂移后的症状**
点击导航跳转后右侧高亮停在上一段；或段标题被吸顶导航压住／紧贴浮层下沿。

**历史故障（两轮）**
1. 停靠位 64px（`scroll-mt-16`）而判定线 128px → 跳转后高亮停在上一段，要再滚一下才切。
2. 两者统一 80px，但手机端吸顶导航正好占 `0..80px` → 标题紧贴浮层下沿、零间隙。
   实测手机端浮层高度 = `mt-3` 12px + `h-14` 56px + header 自身高度。

**为什么不用原生 `href="#id"` 的默认行为**
实测（生产构建、多视口、页面静定后）：**首次原生 hash 跳转会少滚一段**，
落点偏差 30–130px；第二次才正确。改用 `scrollIntoView({behavior:'smooth'})` 手动滚同样如此。
但 `behavior:'instant'` 每次都对 —— 属于浏览器在布局收敛期的行为，不是偏移量算错。
因此 `useAnchorScroll` 采用「平滑滚动 + 停稳后校验 + 偏差则 instant 纠正」，
并用 `history.replaceState` 写 URL，避免原生锚点滚动与自己的滚动打架。
深链直接打开（URL 带 `#id`）由 `useDeepLinkCorrection` 做同样的静默纠正。

**首屏也参与侦测**
`#top` 现在排在 `SECTIONS` 第一位但 `isChapter: false`：
它在右侧导轨上有节点（合并了原先独立的「返回顶部」↑，位置由比例算出）、会被高亮，
但不计入 `01/06` 编号、也不进移动端底部 Tab Bar。
`SECTIONS`（含首屏）用于滚动侦测与导轨；`CHAPTERS`（不含首屏）用于编号与 Tab Bar。

**还有一个「页面滚不动」的坑**
`#contact` 是最后一段，下面只有页脚。实测桌面端页面最大滚动量比所需少 45px、平板端少 258px，
导致它**滚不到停靠位**。这不是偏移量的问题，因此 `Contact.tsx` 末尾加了一段不承载内容的
收尾呼吸区（`h-[clamp(6rem,22vh,16rem)] sm:h-[clamp(8rem,30vh,20rem)]`）。
改动 Contact 内容长度或页脚高度后需重测 `#contact` 落点。

**怎么改**
只改 `scrollTargets.ts` 的值：`@utility` 与侦测线都读同一组值。
**不要**再在组件里写 `scroll-mt-*`。

**怎么验证**

```bash
npm run build && npx vite preview --port 5280
# 逐视口"真实点击"每个导航项，检查 段顶 y == 期望偏移 且高亮对应
```

判定标准：Δ 必须为 0（手机 112px、≥640px 104px）；回到顶部后 `scrollY == 0` 且首屏节点高亮。
注意 `#top` 的段顶在手机端并不等于 0 —— 吸顶导航占 `0..68px` 布局空间，
所以要验证的是 `scrollY == 0`，不是 `#top` 的 `getBoundingClientRect().top`。

## 7. 内容只读白名单

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/hooks/useReadOnlyGuard.ts` | 默认拒绝 + `data-copyable` 白名单；拦截 copy / selectstart / contextmenu / dragstart |
| `src/index.css` | `body { user-select: none }` + `[data-copyable] { user-select: text }` |
| `src/components/Contact.tsx` | 两个邮箱元素标注 `data-copyable` |
| `src/components/Docs.tsx` | **整个 UE 文档区正文容器**标注 `data-copyable`（笔记是给人读的，必须能选中复制） |

**漂移后的症状**
要么全站可被一键全选带走（保护过弱），要么连邮箱都复制不了（阻断核心任务）。
两种极端历史上都出现过。

**怎么改**
要放行新的可复制字段，**给那个元素加 `data-copyable`**，不要放开全局。

**怎么验证**
`body` 的 `user-select` 应为 `none`、邮箱 span 应为 `text`；
在正文上派发 `copy` 事件应被 `preventDefault`，在邮箱上应放行。
剪贴板实测必须用**可信点击**（CDP `Input.dispatchMouseEvent`）：
`element.click()` 不是可信手势，`navigator.clipboard.writeText` 会抛 `NotAllowedError`，
不要把它误判成功能坏了。

## 8. 数据库 ↔ JSON 数据源

**涉及文件**

| 文件 | 角色 |

| `database/portfolio.db` | 内容源（README 声明） |
| `src/data/*.json` | 构建数据 |
| `scripts/seed-db.mjs` | JSON → DB |
| `scripts/export-db.mjs` | DB → JSON（`npm run build` 自动执行） |

**漂移后的症状**
直接改了 `src/data/*.json` 但没跑 `db:seed` → 下次 `build` 时 `db:export` 用数据库覆盖你的修改。

**怎么改**
两条路选一条，不要混：

- 改 JSON → `npm run db:seed`
- 改 DB → `npm run db:export`

`npm run build` 含 `db:export`，所以**数据库始终是最终赢家**。

## 9. 预览页注入 ↔ 预览产物

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `scripts/polish-previews.mjs` | 注入演示提示条 + iframe 防护（幂等） |
| `public/preview/<id>/index.html` | 注入目标 |

**漂移后的症状**
重新构建复制预览产物进 `public/preview/` 后，注入内容被覆盖，演示提示与 iframe 防护消失。

**注意：横幅位置有两套策略，按页面类型分**

| 模式 | 适用 | 做法 |
| --- | --- | --- |
| `FLOW_MODE` | 普通文档流、**可滚动**的页面（book-recommendation） | 横幅占流插入，内容自然下移 |
| `RESERVE_MODE` | **固定视口**、不可滚动的页面（milu-studio / milu-assistant-web / xiao-lou-ai / sylab-ai） | 横幅仍 `absolute` 浮层，但宿主容器按 CSS 变量 `--demo-note-space` 让出等高的 `padding-top` |

为什么固定视口不能也用占流：那类页面 `文档高 == 视口高`，横幅占流会把应用内容挤出可视区。
而只浮层不让位又会遮挡应用自己的工具栏 —— 实测 milu-studio 1440×900 横条 66–131、
应用线程壳 54–900，顶部 65px 被盖住。所以改为「浮层 + 宿主预留空间」。
预留量的测量要**先把变量归零再量**，否则会把上一次的 padding 算进去逐次累加。

**⚠️ 模式开关必须是布尔值，不能是字符串**
`flowMode` 曾经写成 `'true'/'false'` 字符串，而 `'false'` 是**真值**，
导致 `flowMode ? A : B` 判断整个反向（本文件历史上踩过一次）。

**iframe 防护包含两个元素**
CSP meta + frame-busting script。清理时必须**分别擦除**，
只擦 script 会让 meta 在每次重跑时累积（实测第二轮就出现两份 CSP）。

**怎么改**
预览产物更新后重跑：

```bash
npm run previews:polish
```

改完自检：`vite preview` 起服务后访问 `/preview/milu-studio/`，
确认宿主的 `padding-top` 等于横幅高 + 12，且横幅不再压住应用工具栏。

## 12. 首屏以下的延迟渲染 ↔ 锚点/导轨测量

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/index.css` → `.cv-section` | `content-visibility: auto` + `contain-intrinsic-size` |
| `src/components/Skills.tsx` / `Experience.tsx` / `Education.tsx` | 内容容器上的 `.cv-section` |
| `src/components/SideDotsNav.tsx` | 导轨节点比例与液柱进度（依赖文档高度） |
| `src/hooks/useScrollSpy.ts` | 滚动侦测（依赖各 section 的 `getBoundingClientRect`） |

**为什么这么加**
首屏只需要 Hero，但整页有 7 个区块、几十张卡片。`content-visibility: auto` 让浏览器跳过
首屏以下子树的初始布局与绘制，并在离屏后回收 —— 这是本页体量最大的一类优化。

**⚠️ 三条约束（改动时必须同时满足）**

1. **只加在区块内的内容容器上，不加在 `<section>` 上。**
   锚点停靠（`scroll-anchor-offset` 的 `scroll-margin-top`）挂在 section 上；
   导轨的节点比例也是按 section 的 `offsetTop` 算的。section 必须保持正常布局。
2. **`contain-intrinsic-size` 不能省。** 没有它，未渲染子树的自然尺寸按 0 计，
   文档高度会随滚动不断变化（滚动条"长出来"），比不做优化更糟。
   当前值 `auto 2200px` 取的是移动端最长区块（技能区）的近似高度，**宁可高估不要低估**：
   高估只是滚动条一开始偏长，低估则会一路变长。`auto` 关键字会让浏览器在区块渲染过一次后
   记住真实尺寸，第二个来回起不再有偏差。改版式后可重新用 DevTools 校准（不是硬约束）。
3. **首屏 Hero 与紧随其后的 About 不加。** About 内部有链路卡的 IntersectionObserver
   与连接线绘制，依赖真实布局。

**漂移后的症状**
导轨节点位置整体偏上/偏下、液柱与节点错位；或 `#contact` 滚不到停靠位；
或滚动条在滚动过程中跳动。

**怎么验证**
`npm run build && npx vite preview`，然后逐视口点击每个导航项：
判定标准与第 6 条相同（Δ 必须为 0），并额外确认滚动条总高度在滚动前后一致。

## 13. UE 学习笔记：本地原文 → 站点文档区

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `C:\Users\10045\Desktop\ue5-notes\*.md` + `images\` | **原文唯一来源**（Typora 维护，不在本仓库） |
| `docs/ue5/source/*.md` | 导入站点的原文快照（提交进仓库，CI 不依赖桌面目录） |
| `_archive/ue5-notes/images/` | 原始 PNG 归档（站点不引用，`public/` 只放 WebP） |
| `scripts/optimize_images.py` | PNG/JPG → WebP（长边 1600、质量 82，幂等） |
| `scripts/import-ue-docs.mjs` | markdown → HTML + 大纲 + `src/data/ue5-docs.json` |
| `public/docs/ue5/*.html` + `images/**/*.webp` | 文档区实际加载的资源（fetch 注入 DOM） |
| `src/components/Docs.tsx` + `src/hooks/useDocsRoute.ts` | 文档区视图与 `#/docs/ue5/<id>` hash 路由 |

**更新一篇笔记的顺序（顺序不能乱）**

```bash
# 1) 把新原文覆盖到快照目录（原文仍在桌面目录里编辑）
copy "<桌面>\ue5-notes\<name>.md" docs\ue5\source\<name>.md
# 2) 转图片（幂等，只处理新增/变更的；中文路径必须用 --only-from-md 传，别用 --only）
python scripts/optimize_images.py _archive/ue5-notes/images public/docs/ue5/images --only-from-md docs/ue5/source/<name>.md
# 3) 生成 HTML + 大纲（脚本会自检：引用了但没转出来的图片会直接报错退出）
node scripts/import-ue-docs.mjs
# 4) 新汉字要进字体子集，否则回退系统字体
npm run fonts:subset
npm run build
```

**新增一整篇文档**：先把 `DOCS` 表里该篇的 `status` 改成 `ready`（`scripts/import-ue-docs.mjs`），再走上面四步。
`status: 'pending'` 的篇目只显示标题 + 「待导入」标记，链接不可点（避免死链）。

**漂移后的症状**
- 忘了第 3 步 → 站点还是旧内容（但构建成功，不会报错）；
- 忘了第 4 步 → 新文章里的字显示成系统字体，与全站不一致；
- 图片路径对不上 → 页面出现裂图（第 3 步的自检会拦下来）。

**为什么自己写转换器而不是引 marked**：这批笔记的方言只有标题/列表/粗斜体/行内代码/图片/链接
（实测五份文档里 HTML 标签**只有 `<img>`**，无代码块、无表格、无引用块、无 script/事件属性），
但有三处非标准写法（Windows 反斜杠路径、文件名里的零宽空格、互链缺 `.md`），
引库还要再写三个插件，不如让转换器顺手处理掉并产出大纲。

**⚠️ 复制白名单**：文档区正文容器带 `data-copyable`（见第 7 条）——笔记是给人读的，
必须能选中复制；改这个属性会直接破坏文档区的核心用途。
