# 联动维护点

本站有几处「同一个事实写在两个地方」的设计。它们本身是必要的（为了首屏性能、无闪烁、静态部署），
但**改动时必须成对修改**，否则会出现难以定位的症状。这份文档把它们集中列出来。

每一条的格式：**联动点 → 涉及文件 → 漂移后的症状 → 怎么改 → 怎么验证**。

---

> ⚠️ **2026-09 第五轮：静态 Hero 骨架已删除**（index.html 里那段 `<style id="hero-shell-style">` 与 `#root` 内的 `<section class="hero-shell">`）。
> `check-hero-skeleton.mjs` 与它约束的「骨架盒模型必须与 Hero.tsx 逐项一致」这条契约**已作废**，不要再按它维护。
> React 挂载前的空窗现在由 `#boot` 加载页独占，见 DESIGN.md 的 The Boot-Screen Rule。
## 1. 首屏骨架 ↔ 真实 Hero

**为什么存在两份**
`index.html` 里的 `<style id="hero-shell-style">` + `<div id="root">` 内的骨架，
用于消除 JS 加载期的白屏。它必须独立生效，所以不能依赖外部样式表，只能手写一份等价 CSS。

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `index.html` → `<style id="hero-shell-style">` | 骨架样式（手写 CSS） |
| `index.html` → `<div id="root">` 内的 `<section class="hero-shell">` | 骨架 DOM |
| `src/components/Hero.tsx` | 真实 Hero（React） |
| `src/index.css` → `@theme` 的 `--text-*` | 流体字号来源（骨架的 `clamp` 值抄自这里） |

**漂移后的症状**
首屏刷新时文字「跳一下」：位置、宽度或字号在 React 挂载瞬间变化。

**历史故障（实测数据）**
2026-09 修过一次：骨架 H1 写到 `y=104`、真实 Hero 在 `y=188`，挂载瞬间**下移 84px**；
副题块宽度从 1120px 收到 896px（**横向收窄 224px**）。原因是六处盒模型不一致：
内容缺 `max-w-4xl`、内边距写死、`min-height` 用 `62vh` 而非 `100svh - 4rem`、
H1 字号写死 `4.25rem` 而非 `clamp()`、字重写成 900（app 是 400）、
`justify-content` 与 app 的 `sm:justify-center` 不一致。

**当前约定（重要）**
骨架的**内容列 `.hero-col` 设为 `visibility: hidden`**，骨架只负责背景层与光斑。
原因：app 的首项位置 = `0.706 × 容器高度`，而容器高度 = `max(731px, 100svh - 4rem)`。
这是一个随视口高度连续变化的比例，骨架无法用与容器高度同源的度量复现它。已逐一验证并排除：

| 方案 | 实测偏差 |
| --- | --- |
| 固定 px | 640–1500px 视口高度区间内偏差 12–818px |
| 百分比 `padding` | 按**宽度**解析而非高度，偏出 900px 以上 |
| grid `fr` 轨道 | 单行自动放置时轨道塌陷，偏差 56–409px |
| `vh` / `svh` | 生产环境可响应，但无头仿真下不随视口变化，无法回归验证 |

所以**不要再尝试对齐骨架的文字位置**。骨架不渲染前景内容，就没有可错位的东西。

**怎么改**
- 只改 `Hero.tsx` 的视觉样式（颜色、圆角、图标）→ 无需动骨架
- 改 `Hero.tsx` 的**背景层**（光斑位置、网格）→ 同步改 `.hero-shell::before`
- 改首屏文案 → 同步改骨架 DOM（虽然不可见，但改掉更省心；文案也会影响 `subset-fonts` 的字符集）
- 想恢复骨架显示文字 → 必须同时满足：两处盒模型逐项一致 **且** 能接受垂直方向仍有偏差

**怎么验证**

```bash
npm run build && npx vite preview --port 5231
# 逐断点比较「骨架阶段」与「应用稳定后」的 H1 视口坐标
node <诊断脚本> http://localhost:5231/ 1440 900
```

判定标准：`x` 与宽度必须为 0 误差；CLS 必须为 0。

## 2. 首屏内联字体 ↔ 字体子集

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/fonts/*.woff2` | 子集化产物（唯一来源） |
| `scripts/subset-fonts.mjs` | 生成子集 |
| `scripts/inline-firstscreen-fonts.mjs` | 把柳建毛草 + 得意黑 base64 内联进 `index.html` |
| `index.html` → `<style id="font-face-inline">` | 内联产物（勿手改） |
| `vite.config.ts` → `FONT_FILES` | 构建后注入的 `<link rel="preload">` 列表 |

**漂移后的症状**
新增文案的用字不在子集内 → 回退到系统字体，粗细/字形与全站不一致。
或：`index.html` 内联的是旧字体，`src/fonts` 是新的，两者静默不同步。

**历史故障**
内联块原本是**人工粘贴**的、且内联的是子集化之前的旧文件，**没有任何生成器**。
文案变更后重跑子集化，`src/fonts` 更新而 `index.html` 不会。

**怎么改**
改完任何文案后：

```bash
npm run fonts:subset    # = subset-fonts.mjs + inline-firstscreen-fonts.mjs，两步必须成对
```

若新增了**首屏**展示层用字（H1、区块标题），还要看 `vite.config.ts` 的 `FONT_FILES`
是否需要把该字重加入预加载列表。

## 3. 主题初始化 ↔ 主题切换组件

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `index.html` → `<head>` 内联脚本 | 首屏前套用主题，避免闪白/闪黑 |
| `src/hooks/useTheme.tsx` | 主题状态**唯一来源**（Context）+ 同步 `theme-color` + 落盘 |
| `src/components/ThemeToggle.tsx` | 三态下拉（自动 / 浅色 / 深色） |
| `src/components/TopBar.tsx` | 常驻顶栏里的那个实例（**全端、两种视图都有**） |
| `src/components/MobileTabBar.tsx` | 手机端底部 Tab Bar 里的实例 |
| `index.html` → `meta[name="theme-color"]` | 移动端状态栏配色（**只放一个**，由 JS 全权覆写） |

**漂移后的症状**
- 内联脚本与组件判定逻辑不一致 → 首屏闪一下再跳到正确主题
- `localStorage` 的键名或取值集合不一致 → 主题"记不住"
- 画布底色改了但 `theme-color` 没改 → 移动端地址栏与页面脱色
- 主题控件只挂在某个视图上 → **该视图没有主题入口**（2026-09 的实际故障：文档区
  `#/docs` 里三个浮层都不渲染，用户完全改不了主题）

**当前约定（2026-09 起）**
主题控件由 `TopBar` 提供，而 `TopBar` 是**全端常驻**的（不区分视图与断点），
所以任何新视图都会自动获得主题入口。`MobileTabBar` 里那个实例是历史遗留的第二个入口，
保留但不再是必需项 —— 若将来要精简，删它不会造成功能缺失。

**怎么改**
三处的画布色值必须一致：`src/index.css` 的 `body` 背景、`index.html` 的 `theme-bg-inline`、
`useTheme.tsx` 的 `CANVAS`。键名固定为 `localStorage.theme`，取值集合固定为 `auto | light | dark`。

## 4. 色板 ↔ 组件里硬编码的颜色

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/index.css` → `@theme` | 色板唯一来源 |
| 各组件里的 `rgb(...)` / `#hex` 内联 | 装饰性渐变、光晕、SVG 描边 |

**漂移后的症状**
改了色板，但某些渐变/光晕仍是旧色，页面出现两种色系。

**当前已知的硬编码位置**（改色板时逐个检查；下表已按 2026-09 的石墨 + 琥珀改版更新）

| 位置 | 当前值 |
| --- | --- |
| `About.tsx` 多定位卡背景 | `radial-gradient(... rgb(217 122 6 / 0.14) ... rgb(247 189 110 / 0.16))`（= brand-500 / brand-400） |
| `SideDotsNav.tsx` 管体与节点 | `rgba(157,83,0,…)` 系列、`bg-brand-300`、`rgba(242,169,59,…)` |
| `index.css` 的 `.site-bar.is-scrolled` | `0 1px 12px rgb(157 83 0 / 0.06)`（= brand-700） |
| `index.css` 的 `.bar-control:focus-visible` | `0 0 0 2px rgb(242 169 59 / 0.6)`（= brand-300） |
| `index.css` 卡片阴影 | `rgb(157 83 0 / 0.06)` |
| `index.css` 的 `--bar-control-lit-bg` / `--bar-control-lit-fg`（顶栏悬停 + 胶囊选中**共用**） | `rgb(255 255 255 / 0.16)` / `#804400`；深色档 `rgb(255 255 255 / 0.13)` / `#f3d9ac`（= brand-200） |
| `index.css` 的 `--bar-rest-shadow`（顶栏控件静置环境光） | 浅色 `0 0 14px -6px rgb(217 122 6 / 0.18)`；深色 `0 0 16px -8px var(--glass-glow-warm)` |
| `Hero.tsx` 头像 ring | 走 `ring-brand-100`，已是 token ✓ |

> 改主色时**这张表就是检查清单**。历史教训：改色板时漏掉了 `About.tsx` 的光斑与
> 已删除的 `BackToTop.tsx` 进度环，导致页面上同时存在新旧两种色系的装饰层。
> （`BackToTop.tsx` 已在 2026-09 并入 `TopBar`，不再是独立的硬编码点。）


**⚠️ 暖调转向（2026-09 第十二轮）：中性色也必须走 token**

这一轮把整族中性色由**冷石墨**改为**暖石墨**（chroma ≤4%、色相 25–45°），
过程中抓到一批"漏改"——它们的共同特征是**硬编码或独立定义，绕过了色板**。
下次再动中性色，按这份清单逐条核（都已在本轮修掉，列在这里是为了记住"哪里容易漏"）：

| 漏改点 | 原冷值 | 现暖值 | 为什么容易漏 |
| --- | --- | --- | --- |
| `--color-ink`（全站 h1/h2/h3、顶栏站点名） | `#1a1c1e` | `#221f1a` | 它是"墨色"，看起来像有意的黑，不像灰 |
| `--color-ink-light`（深色正文/标题） | `#e6e8e9` | `#ece7df` | 同上 |
| `.bar-control` 的文字色 | `#333a3d` / `#dde0e2` | 改走 `--bar-text`（第十三轮起；此前一度共用 `--chip-text`） | 注释写着"不走 token"，后人不敢动 |
| `--chip-text` 深色档 | `rgb(203 213 225)`（slate-200 冷蓝） | `#cdc2b1`（slate-200 暖米） | 只在深色档出现，浅色档检查时看不到 |
| `.docs-subbar` 底 | `rgb(250 251 251 / …)`（冷白） | `rgb(251 248 243 / …)` | 文档区专属，首页检查时看不到 |
| `--panel-tint` 深色档 | `rgb(27 30 32)` | `rgb(41 37 31)` | 同理，只在深色档暴露 |
| 顶栏/横栏里十余处 `rgb(18 20 21)` | 冷石墨 | `rgb(21 18 15)` | 散落在多条规则里，不是 token |
| `index.html` 的 SVG 滤镜与内联样式 | `rgba(120,140,143,…)` 等 | `rgba(132,116,96,…)` 等 | **不在 .css 里**，全文件搜色值时最易漏 |

> 自查口径：任何"近灰"的颜色，**R 必须 ≥ B**（暖侧）。`B > R` 就是冷灰，一律视为漏改。
> 这句话可以直接当 grep 规则用（见本轮审计脚本的判定条件）。

**顶栏按钮的文字色（2026-09 第十二轮定向 → 第十三轮定稿）**

按钮文字**不再硬编码**：第十三轮起改取 **`--bar-text`**（不再是 `--chip-text`）。
两档都对齐到「**正文 / 标题**」这一个语义槽位：
浅色 = `--color-ink` `#221f1a`（与站点名、Hero 标题同一档）↔ 深色 = slate-200 `#cdc2b1`。

⚠️⚠️ **第十三轮的真问题不在色值，在绘制顺序**（这一条比色值重要得多）：
用户报「浅色模式下文字还是偏淡」时，`.bar-control` 的文字色已经是 `#29251f`，
但**落地像素只有 rgb(147,145,142)**（对按钮底 2.99:1）。变量隔离实测：

| 隔离项（都强制 `color:#000`） | 最暗像素 |
| --- | --- |
| 只改黑字 | rgb(127,127,127) |
| 黑字 + 关 `backdrop-filter` | rgb(127,127,127)（不变） |
| 黑字 + 关 `filter: drop-shadow` | rgb(127,127,127)（不变） |
| 黑字 + 关掉 `.bar-sheen` 的底与 `::before` 面光 | **rgb(0,0,0)** |
| 黑字 + 把字形提到面光之上 | **rgb(0,0,0)** |

说白了：**`.bar-control` 上的 `backdrop-filter` 让控件成了 backdrop root，绝对定位的
`.bar-sheen`（以及它 `::before` 的双层径向面光）于是画到了字形之上**，把 14px 的中文笔画
洗淡了一半。深色档"反而正常"是同一个机制的反面（那里白面光只有 6%）。
修法是 `.bar-control > :not(.bar-sheen) { position: relative; z-index: 1 }` ——
**只改绘制顺序、不动任何材质参数**；`:not(.bar-sheen)` 不能省（sheen 的 `inset: 0` 依赖原参照系）。

⚠️⚠️ **跨主题对齐的是"槽位"，不是十六进制值。** 第十一轮真踩过的坑：
先让两档同取 slate-800 `#29251f`，深色档实测只剩 **1.23:1，几乎看不见**
（深底 `#1a1714` 上压深墨 = 隐形）。深色档的"加深"在观感上等于**提亮**，方向与浅色档相反 ——
这条对任何中性色都成立，不止按钮。

⚠️ 校验手段：`node scripts/check-controls.mjs`（两档 × PC/手机，实测控件与正文对比度，低于阈值报错）。
⚠️ 两个 token 的影响面**不同**，改之前先分清：
`--bar-text` **只服务顶栏四个控件**；`--chip-text` 服务 `.glass-chip` 一族
（技能/项目筛选胶囊、经历标签、文档区控件、手机 Tab Bar）。第十三轮之所以拆开，
就是因为用户只报了顶栏、没提胶囊 —— 改 `--chip-text` 会把这五处一起带走。
建议做法：把这类装饰色收敛为 `index.css` 里的 `--glow-*` 变量，组件引用变量而非字面量。

## 5. 响应式断点：JS 与 CSS 各写一份

**涉及文件**

| 文件 | 断点 |
| --- | --- |
| `src/hooks/useIsMobile.ts` | `(max-width: 639px)` |
| `src/components/Experience.tsx` | `sm:hidden`（640px 起隐藏） |
| `src/components/Hero.tsx` | `sm:hidden` / `hidden sm:block` |
| Tailwind 默认 | `sm = 640px`、`md = 768px`、`lg = 1024px` |
| `src/index.css` 的 `section-*` / `hero-inner` | `@media (min-width: 640px)` |
| `src/index.css` 的 `.rail-gutter` | `@media (min-width: 768px)`（与右侧导轨出现的 `md` 对齐） |
| `src/index.css` 的 `--breakpoint-xl3: 74.25rem` | 自定义断点 1188px，供 `xl3:` 前缀使用（当前仅剩卡片内边距在用） |
| `src/components/SideDotsNav.tsx` 的 `RAIL_QUERY = '(min-width: 768px)'` | 与 `.rail-gutter`、Tailwind `md` 同一个 768px：桌面导轨的出现/隐藏开关，还控制**是否挂载导轨子树** |
| `src/components/Docs.tsx` 的 `md:` / `xl:` 前缀 | 768px 起显示左侧文档树、`xl`(1280px) 起显示右侧大纲；768 以下改为**顶栏下方吸顶的目录入口 + 浮层抽屉** |
| `src/data/navigation.ts` 的 `isChapter` | 决定一个条目是否参与**章节编号**与移动端 Tab Bar。文档区（`docs`）必须为 `false` —— 漏掉它，`CHAPTERS.length` 会变成 7，全站编号都会显示成 `0x / 07` |

**⚠️ 右侧导轨是「条件挂载」而不是「CSS 隐藏」**
`SideDotsNav` 外层 nav 常驻并带 `hidden md:flex`；内部 `Rail` 只在 `RAIL_QUERY` 命中时挂载
（`useRailVisible`，基于 `useSyncExternalStore`，避免首帧按手机渲染再切桌面）。
改这个断点时**必须同时改 `RAIL_QUERY` 和 className**，否则会出现「CSS 说显示、JS 说没挂载」
或反过来的空白导轨。历史上它是 CSS 隐藏、组件照跑：手机上白背一个 scroll 监听（每帧读
`scrollHeight` 强制布局）+ 两个 ResizeObserver + 一个 MutationObserver，见 README 的性能预算。

**链路卡列数：恒定两列 + 容器上限 1024px（已废除三列方案）**
About 的四张「能力链路卡」每张内部有两组「数字 + 后缀」，可读宽度低于约 320px 时
数字与后缀会被挤成两行、正文每行掉到 16 字以内。历史实测（已计入 md 起的导轨留白与容器 padding）：

| 视口 | 三列时每张宽 | 结论 |
| --- | --- | --- |
| 1024 | 280px | 太小 |
| 1188 | 323px | 刚好够（三卡时代取值） |

三卡时代曾用 `xl3`（1188px）切三列。**2026-09 加到四张卡后该方案废除**：
四张卡在 3 列网格里必然排成 3+1，第四张独自占一整行；平板与 1024–1188px 视口
更早就已经是 2+1 的孤卡（这正是当初被反馈的问题）。
现方案：`<640` 单列 → `≥640` **恒定两列（2×2）**，容器 `sm:max-w-5xl`（1024px）居中。
每张约 480px，数字与后缀同行、正文每行 30 字以上。

**改动卡片内边距、容器上限或 `.rail-gutter` 后，这三个数字（320 / 480 / 1024）需要一起重新验算。**

**漂移后的症状**
640px 附近出现「JS 认为是手机、CSS 认为是桌面」的错配：折叠按钮与布局状态对不上。

**当前状态**
`useIsMobile` 用 `max-width: 639px`，与 Tailwind 的 `sm:hidden`（`min-width: 640px` 才隐藏）
**恰好互补，无缝隙**。改动任一处时保持这个互补关系。

**建议**
能不靠 JS 判断的就不靠：优先用 `hidden sm:block` 这类纯 CSS 方案。
`Experience` 的「移动端默认折叠要点」因为需要交互状态才用了 JS，属合理例外。

## 6. 锚点停靠位 ↔ 滚动侦测线 ↔ 导航点击行为

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/data/scrollTargets.ts` | 偏移量**单一来源**（手机 112px / ≥640px 104px，= TopBar 64 + 间隙） |
| `src/index.css` 的 `.anchor-offset` | 用上面的值生成 `scroll-margin-top`（**普通类 + 显式 @media**，见下方「不要用 @utility」） |
| `src/components/TopBar.tsx` | 常驻顶栏，`h-16`（64px）—— **偏移量的几何来源**，改高度必须同步改上面两处 |
| `src/index.css` 的 `--site-bar-h` / `--rail-top` | 同一高度的变量化来源（导轨起点也用它） |
| 各 `section` 的 `className` | 统一写 `anchor-offset`，不再各写 `scroll-mt-*` |
| `src/hooks/useScrollSpy.ts` | 读取同一组值作为判定线（+2px 容差） |
| `src/hooks/useAnchorScroll.ts` | 导航点击的滚动实现（见下方「为什么不用原生锚点」） |
| `src/data/navigation.ts` | 首屏 `#top` 也登记为节点（`isChapter: false`）；带 `href` 的条目是跨视图跳转 |
| `src/components/SideDotsNav.tsx` | 节点位置 = 「滚到停靠位时的滚动进度」，与液柱同一度量；**只展示页内章节**（带 `href` 的跨视图条目被 `RAIL_SECTIONS` 过滤掉） |
| `src/components/Docs.tsx` | 文档区的 `HEADER_OFFSET` 与 `.doc-content` 的 `scroll-margin-top` 同样按顶栏高度取值 |

**⚠️ 2026-09 改版的口径变化**
以前只有手机端有吸顶浮层（80px），桌面/平板"无浮层"所以取 88px；
现在 `TopBar` **全端常驻 64px**，三端都按「64 + 间隙」算（手机 112 / 桌面 104）。

**⚠️ 不要用 `@utility` + 嵌套 `@media` 实现**
实测 Tailwind v4 的 `@utility` 会**丢掉嵌套的 `@media`**，只生成基础声明：

```css
@utility anchor-offset { scroll-margin-top: 104px; @media (width >= 40rem) { scroll-margin-top: 88px } }
/* 构建产物只有：.anchor-offset{scroll-margin-top:104px}  ← 88px 那条从未生成 */
```

后果是**桌面端一直在用手机端的 104px**，且因为 `useAnchorScroll` 的「停稳后纠正」机制会把落点补正，
这个错误被掩盖了很久没被发现。同类问题也发生在 `rail-gutter` 上。
现在两者都写成**普通类 + 显式 `@media`**（放在 `@import "tailwindcss"` 之后即可，优先级够）。
自检方法：`npm run build` 后 grep 构建产物，确认两条 media 查询都在。

**漂移后的症状**
点击导航跳转后右侧高亮停在上一段；或段标题被吸顶导航压住／紧贴浮层下沿。

**历史故障（两轮）**
1. 停靠位 64px（`scroll-mt-16`）而判定线 128px → 跳转后高亮停在上一段，要再滚一下才切。
2. 两者统一 80px，但手机端吸顶导航正好占 `0..80px` → 标题紧贴浮层下沿、零间隙。
   实测手机端浮层高度 = `mt-3` 12px + `h-14` 56px + header 自身高度。

**为什么不用原生 `href="#id"` 的默认行为**
实测（生产构建、多视口、页面静定后）：**首次原生 hash 跳转会少滚一段**，
落点偏差 30–130px；第二次才正确。改用 `scrollIntoView({behavior:'smooth'})` 手动滚同样如此。
但 `behavior:'instant'` 每次都对 —— 属于浏览器在布局收敛期的行为，不是偏移量算错。
因此 `useAnchorScroll` 采用「平滑滚动 + 停稳后校验 + 偏差则 instant 纠正」，
并用 `history.replaceState` 写 URL，避免原生锚点滚动与自己的滚动打架。
深链直接打开（URL 带 `#id`）由 `useDeepLinkCorrection` 做同样的静默纠正。

**首屏也参与侦测**
`#top` 现在排在 `SECTIONS` 第一位但 `isChapter: false`：
它在右侧导轨上有节点（合并了原先独立的「返回顶部」↑，位置由比例算出）、会被高亮，
但不计入 `01/06` 编号、也不进移动端底部 Tab Bar。
`SECTIONS`（含首屏）用于滚动侦测与导轨；`CHAPTERS`（不含首屏）用于编号与 Tab Bar。

**还有一个「页面滚不动」的坑**
`#contact` 是最后一段，下面只有页脚。实测桌面端页面最大滚动量比所需少 45px、平板端少 258px，
导致它**滚不到停靠位**。这不是偏移量的问题，因此 `Contact.tsx` 末尾加了一段不承载内容的
收尾呼吸区（`h-[clamp(6rem,22vh,16rem)] sm:h-[clamp(8rem,30vh,20rem)]`）。
改动 Contact 内容长度或页脚高度后需重测 `#contact` 落点。

**怎么改**
⚠️ **没有"只改一处"的办法**（2026-09 更正，之前这段写的是"只改 scrollTargets.ts 即可"）。
这两个值在**四个地方**各有一份，必须同时改，否则就是"改一半"：

1. `src/data/scrollTargets.ts` 的 `MOBILE_ANCHOR_OFFSET_PX` / `DESKTOP_ANCHOR_OFFSET_PX`（JS 判定线）
2. `src/index.css` 的 `.anchor-offset` 两条 `scroll-margin-top`（**硬编码字面量**，不是变量）
3. `src/index.css` 的 `--site-bar-h: 4rem` 与首屏 `calc(100svh - 4rem)`
4. `index.html` 首屏骨架里的 `calc(100vh - 4rem)`（内联关键 CSS，构建期不会同步）

另外**不要**再在组件里写 `scroll-mt-*`（6 个 section 统一用 `anchor-offset` 类）。

> 曾经有一个 `ANCHOR_OFFSET_CLASS` 常量把"类名"抽出来，注释还写着"由 `@utility` 按上面两个值生成，
> 保证不会各改一半"。**那个保证不存在**（`@utility` 方案已被证明不可用，见上），
> 常量本身也零 import。已删除该常量，改为如实列出这四处。
> 要彻底根治得写 `scripts/check-linkage.mjs` 在构建期比对这四处的值（尚未建立）。

**怎么验证**

```bash
npm run build && npx vite preview --port 5280
# 逐视口"真实点击"每个导航项，检查 段顶 y == 期望偏移 且高亮对应
```

判定标准：Δ 必须为 0（手机 112px、≥640px 104px）；回到顶部后 `scrollY == 0` 且首屏节点高亮。
注意 `#top` 的段顶在手机端并不等于 0 —— 常驻顶栏占 `0..64px` 布局空间，
所以要验证的是 `scrollY == 0`，不是 `#top` 的 `getBoundingClientRect().top`。

**注意：横幅位置有两套策略，按页面类型分**

| 模式 | 适用 | 做法 |
| --- | --- | --- |
| `FLOW_MODE` | 普通文档流、**可滚动**的页面（book-recommendation） | 横幅占流插入，内容自然下移 |
| `RESERVE_MODE` | **固定视口**、不可滚动的页面（milu-studio / milu-assistant-web / xiao-lou-ai / sylab-ai） | 横幅仍 `absolute` 浮层，但宿主容器按 CSS 变量 `--demo-note-space` 让出等高的 `padding-top` |

而只浮层不让位又会遮挡应用自己的工具栏 —— 实测 milu-studio 1440×900 横条 66–131、
应用线程壳 54–900，顶部 65px 被盖住。所以改为「浮层 + 宿主预留空间」。
预留量的测量要**先把变量归零再量**，否则会把上一次的 padding 算进去逐次累加。

**⚠️ 模式开关必须是布尔值，不能是字符串**
`flowMode` 曾经写成 `'true'/'false'` 字符串，而 `'false'` 是**真值**，
导致 `flowMode ? A : B` 判断整个反向（本文件历史上踩过一次）。

**iframe 防护包含两个元素**
CSP meta + frame-busting script。清理时必须**分别擦除**，
只擦 script 会让 meta 在每次重跑时累积（实测第二轮就出现两份 CSP）。

**怎么改**
预览产物更新后重跑：

```bash
npm run previews:polish
```

改完自检：`vite preview` 起服务后访问 `/preview/milu-studio/`，
确认宿主的 `padding-top` 等于横幅高 + 12，且横幅不再压住应用工具栏。

## 12. 首屏以下的延迟渲染 ↔ 锚点/导轨测量

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/index.css` → `.cv-section` | `content-visibility: auto` + `contain-intrinsic-size` |
| `src/components/Skills.tsx` / `Experience.tsx` / `Education.tsx` | 内容容器上的 `.cv-section` |
| `src/components/SideDotsNav.tsx` | 导轨节点比例与液柱进度（依赖文档高度） |
| `src/hooks/useScrollSpy.ts` | 滚动侦测（依赖各 section 的 `getBoundingClientRect`） |

**为什么这么加**
首屏只需要 Hero，但整页有 7 个区块、几十张卡片。`content-visibility: auto` 让浏览器跳过
首屏以下子树的初始布局与绘制，并在离屏后回收 —— 这是本页体量最大的一类优化。

**⚠️ 三条约束（改动时必须同时满足）**

1. **只加在区块内的内容容器上，不加在 `<section>` 上。**
   锚点停靠（`scroll-anchor-offset` 的 `scroll-margin-top`）挂在 section 上；
   导轨的节点比例也是按 section 的 `offsetTop` 算的。section 必须保持正常布局。
2. **`contain-intrinsic-size` 不能省。** 没有它，未渲染子树的自然尺寸按 0 计，
   文档高度会随滚动不断变化（滚动条"长出来"），比不做优化更糟。
   当前值 `auto 2200px` 取的是移动端最长区块（技能区）的近似高度，**宁可高估不要低估**：
   高估只是滚动条一开始偏长，低估则会一路变长。`auto` 关键字会让浏览器在区块渲染过一次后
   记住真实尺寸，第二个来回起不再有偏差。改版式后可重新用 DevTools 校准（不是硬约束）。
3. **首屏 Hero 与紧随其后的 About 不加。** About 内部有链路卡的 IntersectionObserver
   与连接线绘制，依赖真实布局。

**漂移后的症状**
导轨节点位置整体偏上/偏下、液柱与节点错位；或 `#contact` 滚不到停靠位；
或滚动条在滚动过程中跳动。

**怎么验证**
判定标准与第 6 条相同（Δ 必须为 0），并额外确认滚动条总高度在滚动前后一致。

**⚠️ 第 3.5 条：滚动容器会裁掉玻璃的泛光（2026-09 第九轮，踩过两次）**

`overflow: auto / hidden / clip` 的盒子会把**视觉溢出**一起剪掉（滚不到的地方就是剪掉），
而 `.glass-lit` / `.glass-lit-on` / `.bar-sheen` 的面光与外发光正是画在盒子外面的。已踩的两次：

| 位置 | 症状 | 处理 |
| --- | --- | --- |
| 项目行的玻璃卡 | 悬停时**底部**被切掉一块，看起来像"玻璃缺了个底" | 祖先不要加 `content-visibility: auto`（它隐含 `contain: paint`），见 DESIGN.md 的 No-Containment Rule |
| 技能区的岗位模板 tablist（`overflow-x-auto`） | 先切**顶部**（当时只有 `pb-1`）；补了上下余量后**左侧**又被切（`padding-left` 实测为 0，第一个胶囊的左边缘与容器左边缘完全重合） | 滚动容器四条边都留余量：`px-2` + `py-1.5` + `scroll-py-1.5`（用户选了"不补偿"，代价是胶囊行比上面的搜索框多缩进 8px） |

口径：**凡是滚动容器里放会发光的元素，四条边都要留出光的余量**（上下至少 6px、左右至少 8px；
横向靠 `scroll-padding` 让滚动落点也不贴边）。
- ⚠️ 不要用负外边距（`-mx-2` / `-my-1.5`）去抵消这份内边距：负外边距会**缩小可滚动区域**
  （overflow 规范里滚动区含 padding、不含负外边距），两端的元素会重新粘住裁切边，比不加还糟。
  —— 技能区 tablist 的问题是**实际宽度够**（1440 下 `scrollWidth == clientWidth`，根本不滚），
  所以"缩进 8px 换取绝对安全"是划算的；只有真正需要贴边对齐时才考虑别的办法。
- ⚠️ 也不要改成 `overflow-x: visible`：移动端的横向滑动会直接失效。
- 想把"有没有被切"变成断言，就在 `scripts/check-anchors.mjs` 里量该元素与它所在滚动容器的
  `getBoundingClientRect()` 之差（左 / 上小于 0 就是被切）。

`prepare-thesis.mjs` 会：抽 41 张插图 → 把「代码表」（Word 里是单元格表格）转成 `<pre><code>` →

**它踩过的两个坑**：

1. 代码表的识别正则一开始写成 `<table>\s*<colgroup>[\s\S]*?</colgroup>…`，
   而 `[\s\S]*?` 是可扩张的 —— 从封面那张表起步一路吃到第五章的 `<th>代码-1</th>`，
   把中间 200 多行（摘要、目录、第 1–4 章）整段当成一个匹配删掉，输出从 93 KB 掉到 39 KB。
   现在必须先按**完整的单张表**切块再在块内匹配。
2. **代码里的实体要还原一次再转义**。pandoc 交出来的是 `&amp;&amp;`，而提取代码时只剥标签、
   再把纯文本 `escapeHtml` 一遍 → `&amp;amp;`，页面上**原样显示 `&amp;&amp;` 和 `&gt;=`**。
   顺序是：先剥标签（否则 `&lt;` 还原出的 `<` 会被当标签削掉）→ 还原实体 → 最后统一转义一次；
   且 `&amp;` 必须**最后**还原。

**新增一篇文档**：在 `build-docs.mjs` 的 `SOURCES` 表里加一条（`section` + `order` + `group`，
有前置写 `prereq`），再走上面四步。
- `order` 是**页在源内的序号**，也是分区内的阅读顺序；篇尾「下一篇」由脚本按分区顺序推导，不用手写。
- `id` **必须等于源文件去掉后缀的文件名** —— 笔记互链写的是 `](./ue5-window-base.md)`，
  解析器只做「反斜杠换正斜杠 → 取最后一段 → 去 `.md`」，id 对不上就会全部降级成「待导入」死文字。
- 「只有标题、没有正文」的源会自动判为 `pending`（实战笔记现在就是这种占位），只显示标题 + 「待导入」，链接不可点。

**⚠️ 顺序不是随意的**：`order` 来自实测的依赖图 —— 总览是入口并指向另外 4 篇；
界面基础与蓝图编程会回引它；界面进阶的前置是界面基础；蓝图编程开头明确建立在「蓝图基础」之上。
**调整顺序前先重跑一次依赖关系核查**（grep 各篇里的互链 + 看开头的承接句）。

**漂移后的症状**
- 忘了先转图片 → 页面出现裂图（`docs:check` 会拦下来）；
- 忘了字体子集 → 新文章里的字显示成系统字体，与全站不一致；

**⚠️ 拆分规则（2026-09 定稿，改之前先读完）**

| 项 | 值 | 说明 |
| --- | --- | --- |
| 预算 | **4 屏/页**（手机口径） | 3 屏是实证上限（NN/g：81% 浏览时间落在前三屏，原文「很少越过第三屏」），但取 3 会把图密集的实操段落切碎；4 屏实测平均 **2.9 屏/篇** |

| 拆不动的叶子 | 如实出页 + 报告里点名 | 原文那一节里没有子标题，**补几个 `###` 就能继续拆** |

**⚠️ 两个「看起来像小问题、其实是功能坏了」的实现约束**（都踩过）：

1. **页面渲染必须用 `fullHtml`（含子孙），不能用 `ownHtml`。** 只取 ownHtml 时，
   「只有标题、正文都在子标题里」的小节渲染出来是**空的** —— 实测 theory 下有 12 个页文件只有
   46 字节（一个空 span），而清单里的字数还是对的（字数是自底向上累计的），
   于是"清单说有 390 字、打开页面什么都没有"。
2. **markdown 源的块必须自己补标题元素。** pandoc 的 HTML 段落是**从 `<hN>` 开始切**的，
   标题天然在里面；而 markdown 段落只存正文。漏补时 md 源的页面里一个标题都没有
   —— 正文糊成一片，右栏大纲也空。

**⚠️ 源 ↔ 产物必须逐条对账**（`check-docs.mjs` 第 6 节）

装箱是"把一棵标题树重新装箱"，一旦漏掉一个分支，**构建照样成功、页面照样能开**，
只是那几节内容再也不出现在站点上。这类丢失只能靠"拿源去数产物"发现，
而且是**文档越长、下钻越深越容易出**。所以每次自检都会：

- 从 `docs/<区>/source/` 读源，抽出**每个标题**（md 的 `#{1,4}` / HTML 的 `<h1-4>`）与**每张配图**；
- 扫遍该源的所有生成页，收集页内标题 + 页面标题 + `ancestors` + `labels`；
- 要求源的每一条都能在产物里找到落点。

> 5.1.1 那一页（**"看不见"不是"丢了"**）。两种都要能区分开，所以断言做的是**覆盖率**。

**⚠️ 左栏的层级口径（2026-09 第三轮定稿）**

左栏不是"按篇幅拆出来的页"的平铺列表，而是**文档自己的目录树**：
`源 → 祖先标题（分组）→ 页`。分组的来源是构建期给每页记下的 `ancestors`（祖先标题链）。

| 规则 | 说明 |
| --- | --- |
| **三级主次是倒过来的** | `源（文件名）13px semibold 深色 + 上分隔线` > `页 13.5px medium 中灰` > `分组（文档内标题）12px regular 浅灰`。2026-09 改：以前正好相反（源 11px 浅灰、分组 14px medium），于是**文档内标题压过了文件名**，而文件名才是分隔符 |
| **页不带序号** | 原先是 `01 / 02`（页在源内的序号），和标题自带的章节号（`03 2.新建项目和项目模板`）是两套编号，叠在一起很乱。顺序由分组和上下位置表达 |
| 可折叠，但**默认全展开** | 源与分组各有一个 chevron 按钮（独立的 `<button aria-expanded>`，不与跳转链接抢点击）。折叠状态存 `localStorage['docs.nav.collapsed']` |
| **点击必须一律生效** | ⚠️ 不要在渲染期加"当前页所在分组强制展开"的守卫。加过一版 `isOpen = activeKeys.has(key)` **或** `!collapsed.has(key)`，后果是**当前页所在的那个源点了没反应**（15 个按钮里 1 个是死的，用户反馈"有的折叠生效，有的不生效"）。守卫要解决的问题（收起后当前页在左栏消失）改由 effect 解决：**路由切进被收起的分组时自动展开它** |
| 页面标题 = **主题标题** | 取页内**第一个非祖先块**的标题。⚠️ 不是"第一个块的标题" —— 拆出来的页往往以容器标题开头，直接取会把标题写成章名（「2 系统相关技术介绍」），而这一页实际装的是 2.1 大数据平台，真正的主题反而看不到 |
| **正文从主题标题本身开始** | ⚠️ 这条绕了两圈才定下来（2026-09）。正文是"块的拼接"，拆出来的页常常以 **1~3 个祖先标题块**开头（下钻时父块的标题会并进第一个子页，父的父也会）。现在：**祖先标题全部去掉**（层级由页头面包屑表达）；**主题标题留在正文里、保持源文件里的原始层级**。踩过的两个坑：① 只删第一个祖先 → 主题标题留在正文里与页头重复（实测 16 页）；② 把主题标题也删掉、改由页头显示它 → **被抽去当页头的那一个标题比同级兄弟高一级**：论文 2.2 页装着 2.2 / 2.3 / 2.4 三个**平行**小节，2.2 成了页头 h1，2.3、2.4 留在正文是 h2，同级看起来像父子。<br>`check-docs.mjs` 第 7 节把"正文首个标题**就是**页面标题、且不是祖先"钉死了 |
| **页头只回答「我在哪」** | 页码 + 来源文档名 + 面包屑 + 前置 + 配套项目，**不再显示页面大标题**（它已经回到正文里）。<br>⚠️ 页面仍需一个 h1：页头放 `<h1 className="sr-only">`（视觉隐藏、读屏与爬虫可见），否则整页没有一级标题、文档结构不合法。<br>⚠️ 正文第一个标题要去掉上边框与上留白（`index.css` 的 `#doc-top + h1..h4` 规则）—— h2 的 `border-top` / `margin-top: 2.75rem` 是给"跟在正文后面的 h2"设计的，出现在卡片开头就是一条多余的横线加一片空白 |
| 「文档标题」那一层不进左栏 | 一份源只有一个顶层标题时（如「虚幻引擎界面基础操作」），它和源标题说的是同一件事。多顶层标题的源（毕业论文有 10 个 H1）那些 H1 是**章**，必须留着当分组 |
| 单子页分组自动拍平 | 分组下只有一个页、且没有子分组时，把这一页提上来单独成行（「2.创建蓝图」这种只挂一节的分组，多一层缩进只会让左栏更长更碎） |

| 悬停提示带「还包含」 | 装箱会把相邻小节并成一页，页标题只取得下第一个；`labels` 字段记着本页实际装了哪几节 |
| 当前页的小节内联在左栏 | 否则同页的其他小节（如 5.1.2）在左栏完全看不到。`xl:hidden` —— xl 及以上右栏已经有「本篇大纲」，两处同时列同一份清单是重复 |
| **右栏大纲：实际标题 ≤ 2 条就不渲染** | 用户 2026-09：「一两条的目录太死板」。实测 56 页里 39 页属于这种情况。⚠️ 但要**保留第三列的列位**（`<aside className="hidden xl:block" aria-hidden />`）—— 撤掉列会把这 224px 让给正文，正文一下子涨到 1118px（70 字/行），而且每页宽度还不一样 |

**⚠️ 正文里的文档互链是路由链接，不是页内锚点**

`onContentClick` 的选择器必须是 `a[href^="#"]:not([href^="/"])`。
早先写的是 `a[href^="#"]`，把 `#/docs/<分区>/<页>` 这种路由链接也接管了 ——
`preventDefault` 之后拿 `/docs/theory/…` 去 `getElementById`，找不到就回落到 `doc-top`：
**既不换页也不报错，只是原地滚了一下**。实测全站 9 条互链全部失效了很久。
另外 `scrollToAnchor` 现在**只在 `id === 'doc-top'` 时**才回落，别的 id 找不到就什么都不做 ——
正是这个"宽容的回落"把上面那个 bug 藏住了。

**⚠️ 篇尾「下一篇」按清单顺序推导，绝不能按 `order` 排序**

```js
// ❌ 错：order 是「页在**源内**的序号」，每个源都从 1 开始
manifestPages.filter(p => p.section === s.id).sort((a, b) => a.order - b.order)
// ✅ 对：清单本身就是按「源顺序 → 源内页序」产出的，filter 已经保序
manifestPages.filter(p => p.section === s.id)
```

按 `order` 排会把各源的"第 01 页"排到一起，于是 `next` 永远指向**下一个文档的同一序号页**。
实测：`[theory/unreal5-notes] #1 一、概况说明 -> next: 1. 菜单栏`（跨到了「界面基础操作」）。
论文只有一份源，所以那一档是唯一正确的 —— 这类 bug **只在多源的区里露头**。

同一个错误在 `Docs.tsx` 的左栏 `pages` useMemo 里也犯过一次（见那边的注释）。
**规矩：`order` 只用于显示「第几节」或排序**同一个源内**的页，跨源比较没有意义。**

篇尾文案跟着 `sameDoc` 走：同一份文档里翻页叫 **「下一节：<页标题>」**，
跨文档才叫 **「下一篇：<源标题>」**（拿下一页的标题当"下一篇"的名字会让人以为还是同一份文档）。

**⚠️ 大纲的层级表达口径**（第二轮定稿）：**只用缩进 + 字号/字重**，每级缩进 12px；
一级 12px 半粗、二级 12px 常规、三级 11px 灰 —— 靠**明度差**读层级。
第一版试过 `├ └` 字符 + 1px 竖线，观感偏"文件管理器"，已废弃；
参考的那种带图标与折叠三角的树属于应用侧栏范式，搬进 224px 的网页大纲里显得沉重，也不采用。
三级降到 11px 不是随手取的，是为了保证**全部标签不换行**（实测 34/27 项零换行、零截断）。

**⚠️ 桌面端是「固定外壳 + 内部滚动」，不是一个会滚的页面**（2026-09 新增，改动风险最高的一处）

用户明确要求「把左侧那一栏（返回作品集 + 5 篇笔记 + 导航）连带着一起固定住」，
实现方式是桌面端把**页面滚动换成容器滚动**：

| 部件 | 位置 | 作用 |
| --- | --- | --- |
| `html.docs-shell` | `useDocsRoute.ts` 用 `matchMedia('(min-width: 768px)')` 开关 | `index.css` 里对 `html` 与 `body` 设 `overflow: clip`，让**页面本身不滚** |
| `.site-bar.is-fixed` | `TopBar.tsx` 在文档区加这个类 | 页面不滚了 `sticky` 就无从粘起，顶栏必须改 `position: fixed` |
| 顶栏占位 `h-16` + **文档区横栏** | `Docs.tsx` | 横栏放「返回作品集 + 分区切换」。⚠️ **第十轮起它在 `#docs-scroll` 内部做 `sticky`**（不再是滚动容器的兄弟），所以正文会从它下面穿过 —— 见下面「横栏折射」一节 |
| **横栏自己 `sticky`**（`.docs-subbar`） | `index.css` 的 md 媒体查询 + `Docs.tsx` 的类名 | 防「横栏被顶栏吞」的第三道防线，见下面「iPad 上横栏被顶栏吞」 |
| **窗口滚动守卫** | `TopBar.tsx` 的 `pin()` effect | 文档区 md+ 下任何窗口滚动量立刻压回 0（含 `visualViewport` 的 resize / scroll） |
| `#docs-scroll` | `Docs.tsx` 的 grid 容器，`md:overflow-y-auto` | **唯一的滚动容器**；锚点跳转、大纲高亮都读写它而不是 `window` |
| 两栏 `md:sticky md:top-0` + 显式高度 | `aside` 自身 | `top-0` = 贴住**滚动容器**的顶边（它已经在顶栏 + 横栏下面了）。高度写 `h-[calc(100dvh-var(--site-bar-h)-var(--docs-subbar-h))]`，内层再 `overflow-y-auto` |

**⚠️ 横栏折射与"可读性底"（2026-09 第十轮定位置，第十三轮定材质）**

第十轮之前横栏是滚动容器的**兄弟**，于是「顶栏占位 64 + 横栏 48 + 滚动容器」这个纵向布局
让滚动容器的内容**永远从 y=112 开始**，物理上不可能从横栏背后经过 —— 当时实测
`elementFromPoint(700, 70/80/…/130)` 全部返回 `null`，开/关 `backdrop-filter` 的可见差异只有
**0.08%**（顶栏同法是 80.95%）。用户反馈的「横栏没有和顶栏一样的透明 + 折射」就是从这里来的。

**第十轮的修法（现在是唯一事实，别再按旧结论返工）**：把横栏**搬进滚动容器内部**，
并配两个件，少一个都会破：

| # | 做法 | 为什么 |
| --- | --- | --- |
| 1 | 容器上 `md:mt-[var(--site-bar-h)]` + `md:h-[calc(100dvh-var(--site-bar-h))]` | 让滚动容器的**可视顶边**落在顶栏下沿（y=64），横栏于是停在原来那个视觉位置，**视觉零位移**；高度显式写死，不再依赖 `flex-1`（踩过：flex 分配会让它多出几十像素、横栏被顶到 y=80） |
| 2 | 紧随其后一条同高的 `.docs-subbar-spacer`（`md:-mt-[var(--docs-subbar-h)]`） | 给 sticky 元件一个位于阈值**之下**的自然位置；没有它，横栏一开始就在 `top` 之上、会跟着内容滚走。负上外边距让它在文档流里等于零高度，正文起始位置与搬动前**逐像素一致**（实测 112） |

搬完之后正文真的从横栏下面穿过，折射有事可做了；代价是**必须给横栏一层可读性底**，
否则下行正文与横栏里的文字会叠在一起（实测滚到 430 时「1. 版本说明」会从「UE 理论」这个 tab 里透出来）。

**⚠️⚠️ 第十三轮（用户定向）：读数靠底，不靠发光。**

原来那句"补一层浅色晕"是 `filter: drop-shadow(0 1px 3px rgb(255 255 255 / 0.85))`，
**只写在浅色档、深色档漏了覆盖**，于是整条横栏在深画布上被一圈奶白包住
（实测同一像素开/关亮度差 **1.67×**，向下溢出约 12px）。用户口径是
「不需要光晕，就和顶栏保持一致的效果就行，不需要发光」。现在：

| 项 | 值 | 说明 |
| --- | --- | --- |
| `filter` | **`none`** | 与顶栏同口径。`check-anchors.mjs` 有一条断言盯着它必须是 `none` |
| 可读性底 | `background-color` 画布色 **72%**（深色 **62%**） | 用 `background-color` 而不是再加一层 `background-image`，是为了让「渐变底」这一项仍能与顶栏**逐字比对**（材质断言在比 `background-image` / `box-shadow`） |
| 裸文字的贴字描边 | `text-shadow: 0 0 1px var(--subbar-text-halo)` | 「返回作品集」与未选中的分区 tab 是**裸文本**、没有玻璃底可依靠，这层描边只在字形周围 1px |
| `backdrop-filter` | 仍然**不要加**在横栏自己身上 | Blur-Budget 断言 + 它会让元素成为 backdrop root（顶栏那三条坑同理） |

⚠️ **不要为了"让折射可见"再动布局**：正文从横栏下穿过这件事第十轮已经做到了，
再上移滚动容器会让正文前 48px 永久藏在横栏下面，是拿可用性换装饰，不做。

**⚠️⚠️ iPad Safari 上「返回作品集被顶栏吞掉」（2026-09 第八/九轮，用户实机反馈）**

用户原话：「进毕业区的毕业论文 → 点跳转 book → 在 book 区再跳回毕业区，顶部返回作品集那一栏
就会被顶栏吞掉，没法操作」。36 组视口的几何扫描（Chrome/CDP）全部正常，说明不是算错，而是
**文档区的窗口被滚下去了**：

- `html.docs-shell { overflow: clip }` 是"页面不滚"的唯一保证，而 **`clip` 是 Safari 16.4 才支持的取值**，
  更早的 iOS Safari 会把整条声明丢弃 → 文档区退回普通可滚页面；
- 横屏地址栏收放会让 `100dvh` 变化、`body` 被撑到比可视区高；橡皮筋回弹也会留下残留滚动量；
- 此时顶栏是 `position: fixed`（钉在 `top: 0`），而横栏当时**不吸顶**，于是滑到顶栏底下 ——
  「返回作品集」正好落在顶栏那 64px 里，点不到。

**三道防线，任何一道单独生效都不会再出现那个现象**（改动时不要只留一道）：

| # | 位置 | 做法 | 为什么不能省 |
| --- | --- | --- | --- |
| 1 | `index.css` 的 md 媒体查询 | `overflow: clip;` 后面紧跟 `overflow: hidden;`（**顺序不能反**） | 不支持 `clip` 的 Safari 拿到 `hidden`；现代浏览器仍命中 `clip`。⚠️ 两条都给 `html` 与 `body` —— 只给 body 会让 body 变成一个内容溢出的滚动容器（实测多出 124px 可滚高度） |
| 2 | `Docs.tsx` 的横栏 + `index.css` 的 `.docs-subbar` | `position: sticky; top: var(--site-bar-h); z-index: 40`，并补一层画布色的**可读性底**（浅色 72% / 深色 62%；第十三轮起由它替代原来那句白色 drop-shadow） | 即使窗口真的被滚下去，横栏也只停在顶栏下沿，绝不会滑到它下面。⚠️ 不要给它加 `backdrop-filter`（Blur-Budget 断言 + 只在异常态才需要）；也不要再加回 `filter` 光晕（`docs:anchors` 的材质断言会红） |
| 3 | `TopBar.tsx` 的 `pin()` | 文档区 md+ 下监听 `scroll` / `resize` / `visualViewport`，一有滚动量立刻 `scrollTo(0)` | 兜住前两道都拦不住的路径（回弹、地址栏动画、第三方脚本滚窗口） |

**⚠️ 切页/切分区的滚动归零必须是 `useLayoutEffect`**（第九轮从 `useEffect` 改过来）：
`useEffect` 跑在绘制之后，切分区时会先画出一帧"旧滚动位置的新页面"，随后才跳回顶部 ——
那一帧里横栏正好压在顶栏下面，看起来就像横栏被吞了。

**守卫的边界（别写错）**：只在 `html.docs-shell` 存在时压窗口滚动。手机端（<768px）文档区
**本来就是页面在滚**，主站也是 —— 在那里压窗口滚动会把整站滚不动。

**这一条的守卫是断言，不是注释**：`npm run docs:anchors` 里有一组 ——
平板与桌面两档视口 × `#/docs/thesis → #/docs/theory → #/docs/thesis` 三轮，
每轮**故意把窗口强行滚下 220px**，然后断言：`window.scrollY === 0`、
「返回作品集」的 `top ≥ 顶栏底边`、该坐标 `elementFromPoint` 命中的是它自己、`.docs-subbar` 的 `position === 'sticky'`。

**⚠️ `--docs-subbar-h` 只此一处**（`index.css` 的 `:root`）：三栏的高度算式用它，
横栏自己的 `h-[var(--docs-subbar-h)]` 也用它。改一个值就够。
锚点落点**不读**这个变量 —— `Docs.tsx` 直接量横栏的 `offsetHeight`（见下面锚点一节）。

**⚠️ 两栏的高度必须显式、且与真实可用高度一致**

| 写法 | 后果 |
| --- | --- |
| 只写 `flex-1` | 两栏撑到内容高度（实测 20481px），内部滚动不触发，而页面又被 `overflow: clip` 关掉了滚动 → **整个文档区滚不动** |
| `max-h-[calc(100dvh-4rem)]` + `top-16` | 顶边在滚动容器顶下方 64px，底边 = 64+64+836 = 964 > 视口 900 → **最后 64px 永远在视口外**（用户反馈「左栏最底部文本显示不全」） |
| 现在：`top-0` + `h-[calc(100dvh-顶栏-横栏)]` + 内层滚动 | 底边正好落在视口下沿 |

**⚠️ 四处必须一起成立，少一个就是"页面完全滚不动"或"两栏跟着滚走"**：

1. **`overflow: clip` 不能用 `hidden`**：`hidden` 会把根元素变成滚动容器、根滚动位置被夹住；
   `clip` 只裁剪不建滚动容器，`window.scrollY` 归零、`sticky` 语义也不变。
2. **只给 md 及以上加**（`matchMedia` 判断，不是 CSS 类切换）：手机端没有侧栏，
   若也被加上 `clip`，就**没有任何滚动手段**了。三处断点必须一致：
   `useDocsRoute.ts` 的 768 / `index.css` 的 `@media (min-width: 768px)` / `Docs.tsx` 的 `md:`。
3. **滚动容器的高度靠两条 `shrink-0` 占位 + `md:flex-1`**：
   外框 `md:h-dvh`，里面依次是「顶栏占位 `h-16`」与「横栏 `h-[--docs-subbar-h]`」，
   剩下的空间由 `md:flex-1` 拿。**不要再写 `calc(100dvh - var(--site-bar-h))`** ——
   占位条已经补过一次，再减一次就是重复计算，整块内容会上移、空白全落到最底部。
4. **`sticky` 必须加在 `aside` 自身，不要外面套一层 div 再 sticky**（踩过两次）：
   - 给 grid item 加 `align-self: start` → 它缩到内容高度（实测 374px），
     里面那个 sticky 元素的容器只有 374px，**没有可粘的行程**，直接跟着滚走；
   - 不加 `align-self: start` 时 grid item 被拉伸到整行高（15800px），
     但那是 aside 的盒子，套在里面的 div 依然粘不住（sticky 认的是父级内容盒）。
   正解：**aside 保持默认 stretch、自身 `position: sticky top-0`**。
   ⚠️ 给 aside 写**显式 `height`** 不影响粘性（粘性行程来自 grid 区域，不是元素高度），
   但写 `align-self` 会 —— 这两件事不要搞混。

**已知代价（不可绕过）**：容器滚动后，浏览器对文档区的**滚动位置恢复失效**
（刷新回到文首而不是上次读到的位置）；URL 的 `?s=` 仍会跟着变，可分享性保留。

**⚠️ 锚点落点只有一个来源：`--docs-anchor-offset`**（2026-09 新增，这是本轮修的主 bug）

`Docs.tsx` 在挂载时量「顶栏高度 + 文档区横栏高度 + 手机端吸顶条高度 + 16px 间隙」写进
`document.documentElement` 的 `--docs-anchor-offset`，然后三处一起消费它：

| 消费方 | 位置 | 说明 |
| --- | --- | --- |
| JS 滚动落点 | `Docs.tsx` 的 `scrollToAnchor` | 手机端 `window.scrollTo(top − offset)` |
| 原生锚点留白 | `index.css` 的 `.doc-h* { scroll-margin-top }` | 顶栏/横栏/吸顶条高度变了自动跟 |
| 大纲高亮判定线 | `Docs.tsx` 的 `anchorLineTop()` | 桌面端直接量「滚动容器顶 + 它的 `scroll-padding-top`」，手机端读这个变量 |

两端不需要分支：横栏在手机端是 `hidden`、吸顶条在桌面端是 `hidden`，
两者的 `offsetHeight` 自然为 0，同一个公式得出
**手机 64+0+53+16 = 133** / **桌面 64+48+0+16 = 128**。
（桌面这个 128 也正好等于「滚动容器顶 112 + `scroll-padding-top` 16」，与 `anchorLineTop()` 一致。）

**历史故障**：这三个数以前各写各的（JS 96、CSS 96、高亮线 `HEADER_OFFSET 88+8=96`），
而手机端顶栏下面压着一条 53px 的「目录与大纲」吸顶条（占 64..117）——
96 的落点正好**藏在它后面**，用户反馈的"点了目录跳不准"其实是标题被那条横条盖住了。

**⚠️ 文档区的滚动一律用 `behavior: 'instant'`，不要写 `'auto'`**
`scroll-behavior` **不是继承属性**，它写在 `html` 上（`index.css:173`，为主站的平滑锚点），
而 `behavior:'auto'` 的语义是"用计算出来的 scroll-behavior" —— 于是**手机端那条路径一直在做平滑动画**
（桌面端滚的是 `#docs-scroll` 容器，没被设 smooth，反而是瞬时的）。
实测表现：点最远的那个大纲项，450ms 后还没滚完，落点差 7–11px 而且每次不一样。
切页/切视图时的 `scrollTo(top:0)` 同理 —— 写 `'auto'` 会看到"旧页面自己滚回顶部"。

**论文 ↔ book-recommendation 的互链（2026-09 新增，两边都由数据驱动）**

| 方向 | 声明处 | 渲染处 |
| --- | --- | --- |
| 论文 → 项目 | `build-docs.mjs` 的 `SECTIONS[].relatedProject = 'book-recommendation'` | 论文每页页头的「配套项目：<项目名> →」，指向 `#projects` |
| 项目 → 论文 | `projects.docs_url`（`projects.json` → `npm run db:seed` 入库） | `Projects.tsx` 的 `buildProjectActions` 里那个「毕业设计原文」按钮 |

⚠️ 两边都**不在组件里判断 id**：项目名从 `projects.json` 现取，按钮按字段有无决定显不显示。
⚠️ `projects.docs_url` 是**数据库列**，改 `projects.json` 之后必须 `npm run db:seed`，
否则下次 `npm run build` 的 `db:export` 会把它冲掉（第 8 条）。

`check-anchors.mjs` 用 Chrome + CDP（Node 自带 WebSocket，**零依赖**），六组断言：

1. **锚点落点**：逐个大纲项 → 点开目录（手机端先展开抽屉）→ 点项 → 量落点。判定：
   落点误差 ≤ 6px（实测全部 ≤0.5px）；标题**不被吸顶元素遮住**；地址栏 `?s=` 跟着变。
2. **跨文档互链**：逐条点正文里的 `#/docs/...` 链接，断言 **h1 真的换了**且正文渲染出来了。
   （这个 bug 的表现是"既不换页也不报错"，只能靠点出来验。）
3. **侧栏底部裁切**：把每个可见 `aside` 滚到底，断言它的底边不超出视口、
   且最后一项完整可见。（这是「左栏最底部显示不全」的守卫。）
4. **左栏折叠**：逐一点击**每一个**折叠按钮，断言都能收起再展开（不许有"点了没反应"的）；
   再单独验「收起某个源 → 跳进它 → 自动展开且当前页在左栏可见」。
5. **横栏材质**（第十轮加、第十三轮扩）：逐项比 `.docs-subbar` 与 `.site-bar` 的
   `background-image` / `box-shadow`（数值量化到 2 位再比，因为顶栏 `box-shadow` 有 320ms 过渡，
   读到的是插值）。第十三轮补两条：**横栏的 `filter` 必须是 `none`**（发光滤镜在深色档没有对应覆盖时
   会整条发光）、**可读性底必须存在**（`background-color` 既不能全透明、也不能没有）。
   加断言时做过反证：往产物里塞回那句 `drop-shadow`，两条断言立刻红。
6. **导航冒烟 + 跨区互链**：`#/docs` 落到第一个分区、目录点页能换页、空分区显示空态；
   以及**论文 ↔ 项目**两条互链的落点（论文页头「配套项目」→ `#projects`；
   项目卡「毕业设计原文」→ `#/docs/thesis`）。

早先靠 `CHAPTERS.findIndex(s => s.label === eyebrow)` 反查编号，**改一个 label 文案会让章节编号静默消失**
（不报错、构建通过）；且各调用处的 `?? '中文兜底'` 已与 `navigation.ts` 漂移。
现在传 `sectionId`，眉题与编号都由 `SECTIONS` 派生。新增区块时传 id，不要再传文案。

**手机端（<768px）的目录是「吸顶入口 + 浮层抽屉」，不是一个普通按钮**：
入口挂在 `sticky top-16`（正好贴顶栏下沿），抽屉 `fixed top-16 bottom-0` 自带滚动。
**这三个数（`top-16`、`bottom-0`、顶栏 64px）必须与顶栏高度一致** ——
历史故障：入口原来是文档区顶部的一个普通按钮，实测滚到 1200px 后它的 `top = -1112`（完全出视口），
展开的目录块又是 `overflow: visible`，于是读者下滑之后**再也没有任何跳转手段**。
另：抽屉打开时锁 `body` 滚动、ESC 关闭、点遮罩关闭、打开时焦点移入（与 Lightbox 同一套口径）。

**⚠️ `data-copyable` 里的光标要分开写**（见第 7 条）：`cursor: text` 不能挂在 `[data-copyable] *` 上，
它会继承式地压过链接与图片的光标（实测文档内链接全是 `text`，读者看不出哪里能点）。
`cursor: text` 那条必须用 `:where(:not(a):not(button)…)` 包一层把权重清零，否则会压过 `img { cursor: zoom-in }`。

**⚠️ 复制白名单**：文档区正文容器带 `data-copyable`（见第 7 条）——笔记是给人读的，
必须能选中复制；改这个属性会直接破坏文档区的核心用途。

| 配方 | 落地对比 |
| --- | --- |

不要盖住任何可读/可点的东西（右下角那 88px 为了让开右侧导轨，`right` 是 `120px` 而不是 0）；

## 15. 教育背景区块的形状：横条 + 证书 2×2

**涉及文件**：`src/components/Education.tsx`（学校卡与证书栅格的跨列写法）。

**走过三段，最后一段才是定稿，前两段都是坑：**

| 轮次 | 形态 | 结果 |
| --- | --- | --- |
| 第十三轮 | 竖卡（`flex-col`）+ 大图标 48px | 手机上图标独占一行（用户：「图标独占一行，这很不美观」），390 宽下卡片 180px 高、光图标段吃掉 68px |
| 第十四轮 | 横排（图标 28px + 文字），但仍占 3 列中的 1 列 | 手机端好了；PC 端同一毛病（图标底 350.3 → 校名顶 370.3 空掉 20px 的 flex gap）也修掉了。**但左卡仍然空** |
| **第十五轮** | **学校卡跨满整行成横条，证书 2×2 排在下面** | 定稿。用户第 2 次反馈：「PC 端教育背景左侧卡片，现在里面内容过于空了」 |

**为什么"竖卡"这条路走不通**（第十五轮实测，别再回头）：
左卡是 3 列中的 1 列（1024 宽下只有 280px、内容宽 214px），而内容只有 66~86px 高；
行高却被右侧证书的 2×2 撑到 214.5px，于是实测**留白 上 33 / 下 116，空白占卡片 69%**。
换句话说：这张卡的**形状**（竖）和它的**内容**（三行短文本）根本不匹配。

**定稿的写法（三端同一套，不做分端适配）**：

```
外层  grid gap-5  sm:grid-cols-2  lg:grid-cols-3
├── Reveal  sm:col-span-2 lg:col-span-3   学校横条（占满当档全部列）
└── Reveal  sm:col-span-2 lg:col-span-3   证书容器
        └── grid gap-3 sm:grid-cols-2 sm:gap-4   ← 证书 2×2
```

**⚠️ 四条硬约束**（每条都踩过或实拍验证过）：

1. **列宽下限 268px。** 实测证书列宽 → 卡片高：268px 名称一行（99.3px）｜240px 两行（118.5px）｜
   132px 三行（186.8px）。所以**不要**为"更紧凑"把证书改成 4 列并排 ，1440 宽下每列只剩 240px，
   名称必折两行（第十五轮预演过 A4 方案，就是这个结果）。各档实测列宽：
   1440 → 496｜1024 → 432｜768 → 304｜390 → 358（单列）。
2. **横条内容必须左对齐，不要 `justify-center`。** 横条状态下它会把图标 + 文字整体推到卡片中央
   （预演实拍："学校名居中、右侧三分之二全空"）。图标用 `items-start` 对齐到**校名那一行**。
3. **跨列写在 `Reveal` 上**（它是 grid item），且 `sm:col-span-2` 必须对应 `sm:grid-cols-2`、
   `lg:col-span-3` 对应 `lg:grid-cols-3` ，两级各占满自己那一档的全部列，少一级就会在
   768~1023 这一档退回"左一列 + 右二列"的旧形态。
4. **图标与文字并排这条不能回退**（第十三/十四轮的结论）：图标盒 28px + 图标 16px，三端一致。

**怎么验证**（一条命令量完三端）：

```bash

#   ① 学校卡宽度 == 容器宽度（说明跨满）；上下留白相等
#   ② 学校名 1 行（320 宽也不换行）
#   ③ 证书列宽 ≥ 268px、名称 1 行、卡片高 99px；390 以下退成单列（4 行）
#   ④ document.scrollWidth <= innerWidth（没有横向溢出）
```

## 17. 触屏交互层：`:hover` 的能力门 ↔ 滚动照亮 ↔ 按压反馈

**涉及文件**：`src/index.css`（能力门 8 处 / 触屏门 2 处 / `.glass-lit-scrolled` / `.glass-lit-press`）、
`src/hooks/useInViewLight.ts`（两个钩子）、`src/App.tsx`（挂在 `.app-root` 上）。

**用户口径（2026-09 第十四轮）**：「现在手机端和平板端采用的也是 PC 端的鼠标悬停逻辑，
就是你点击才会亮，但是和操作直觉不一致，我希望是屏幕划到哪，或者说用户手机焦点在哪，
哪里就有悬停或者选中的效果」。

**先记住三条事实**（都实测过，不要再靠猜）：

1. **触屏的 `:hover` 会粘住，且滚动不脱开。** iPhone 模拟 + 真实触摸事件实测：
   点按前 `matches(':hover') = false`；点按后 `true`、面光 1、`box-shadow` 换成点亮态；
   再滚开 420px **仍然亮着**，只被后续点击解除。
2. **Tailwind 的 `hover:` 工具类早就自带能力门，本站自定义的那几条没有。**
   产物里能看到 4 个 `@media (hover:hover)` 块，而 `.glass-lit:hover`（全站 34 处使用点）、
   `.bar-control:hover`、`.glass-btn:hover`、文档区链接与配图**都在门外**。
   所以触屏上只有这几处会粘 。这也解释了为什么"有的元素正常、有的元素焊死"。
3. **`hover: none` 不等于 `:hover` 不会匹配。** W3C Media Queries 4 原文：
   *"authors should be careful not to assume that the `:hover` pseudo class will never match
   on a device where `hover:none` is true"*。判据只能是**能力查询**，不能靠猜设备。

**修法（三条一起才成立）**

| # | 做法 | 位置 | 改错会怎样 |
| --- | --- | --- | --- |
| 1 | 每一条自定义 `:hover` 包进 `@media (hover: hover) and (pointer: fine)` | `index.css`（8 处门） | 漏一条 → 那一条在触屏上继续粘死 |
| 2 | `:hover` 从 `.glass-lit.glass-lit-on` 那一组里**拆出去**，`:focus-visible` 与 `[aria-*]` 留在原位 | 同上 | ⚠️ 一起包进门 → 键盘用户失去焦点反馈、选中态在触屏上消失 |
| 3 | 触屏补两级：`.glass-lit-scrolled`（滚动照亮）+ `.glass-lit-press`（按压） | 钩子加类 + 触屏门里的规则 | 少了 → 触屏只剩"点一下，什么都不亮" |

**滚动照亮的四个参数（改之前先读，每个都有实测理由）**

| 参数 | 取值 | 为什么 |
| --- | --- | --- |
| 判定 | 与视口**中线最近**的那一个 | 按"进入视口"在一屏 3~4 张卡时会同时点亮好几块，读起来是"整页在闪" |
| 锚点 | 视口高度 **42%** | 手机上底部压着 Tab Bar（约 90px），几何中线落在它后面，按 0.5 算会稳定地"亮下面那张" |
| 观察方式 | IntersectionObserver（整视口为根），**不监听 scroll** | 滚动过程零 `getBoundingClientRect`；进出各回调一次 |
| 候选集 | 活的：进出视口由观察器增删 + MutationObserver 补 `observe` | `.glass-lit` 是动态的（筛选重建、文档区正文运行时 fetch） |

**⚠️ 桌面端两道门都要留**：钩子里 `matchMedia('(hover: hover)')` 直接 return（省掉无谓开销），
CSS 里 `.glass-lit-scrolled` 只在 `@media not all and (hover: hover)` 内生效（鼠标环境下加了类也无视觉变化）。
实测 1440 宽滚动时 `.glass-lit-scrolled` 数量恒为 **0**，而 hover 照常亮。

**⚠️ 两类元素被排除在照亮之外（2026-09 第十五轮，用户定向）**

口径从"凡带 `.glass-lit` 就都接"收紧为"**除筛选胶囊与文档区目录外都接**"。
排除机制是给元素加 **`data-scroll-lit="off"`**，钩子用
`.glass-lit:not([data-scroll-lit="off"])` 选择候选。为什么用属性而不是类名：
语义自解释（"这一块不要滚动照亮"），而且不会被 Tailwind 的工具类排序或 `class` 字符串拼接弄丢。

| 排除族 | 具体元素 | 位置 | 为什么排除 |
| --- | --- | --- | --- |
| 筛选胶囊 | 项目区岗位方向、技能区岗位模板 tab、技能区高频标签 | `Projects.tsx` / `Skills.tsx`（共 12 个元素） | 照亮材质（琥珀描边 + 淡琥珀底 + 琥珀字）与 `glass-chip-on` 的**选中态几乎一样**，实拍确认会被读成"这个筛选项被选中了"；而琥珀在本站代表"可用 / 当前 / 关键" |
| 文档区目录 | 左栏分区列表、左栏页树、顶部分区 tab | `Docs.tsx`（平板触摸下实测 40 个元素） | ① 它们躺在**自己的滚动容器**里（`overflow-y-auto`），而照亮按**视口中线**判定，在那种容器里等于"永远亮最上面那一项"，没有意义；② 当前项的选中态本来就常驻点亮，再叠一层会分不清"我读到这里"与"我停在这一页" |

**不排除的**：卡片、项目行、证书卡、联系区入口、顶栏控件、手机 Tab Bar、文档区正文里的动作件。
它们被照亮没有第二重语义可混淆。

⚠️ 报告观感问题时**不要**改用"给照亮换一套更淡的材质"来收尾：那会破坏
「选中 = 把悬停效果固定住」这条从第八轮就定下的规则（选中与悬停必须逐字相同）。
该让路的是"哪些元素参与照亮"，不是"照亮长什么样"。

⚠️ 新增带 `.glass-lit` 的组件时先问一句：**它有没有"当前项"语义，或者它是不是躺在自己的滚动容器里？**
两条占一条就加 `data-scroll-lit="off"`（判据与验证方法见下）。

**怎么验证**（口径固定下来，别再手测）

```bash
npm run build
# 触屏（iPhone 模拟 + 真实触摸事件）：
#  ① 点一个"当前没被照亮"的 .glass-lit，断言它不会因此亮起（这是本方案的关键前提）
#  ② 滚动若干位置，断言 .glass-lit-scrolled 数量恒为 1，且它跨过视口 42% 那条线
#  ③ 把某个"排除项"滚到正对中线，断言亮的是**它下面那张卡**而不是它自己
#  ④ pointerdown 断言 .glass-lit-press 出现（排除项也要有）、抬起后消失
# 桌面（1440）：
#  ⑤ mouseMoved 到卡片上断言 hover 亮起；滚动后断言 .glass-lit-scrolled 恒为 0
```

它是"交互行为"而不是"几何/材质"，做成断言的成本高于收益。真要固化的入口是
`scripts/check-anchors.mjs`（它已经有 CDP 与触摸模拟所需的一切）。
