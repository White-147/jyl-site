# 联动维护点

本站有几处「同一个事实写在两个地方」的设计。它们本身是必要的（为了首屏性能、无闪烁、静态部署），
但**改动时必须成对修改**，否则会出现难以定位的症状。这份文档把它们集中列出来。

每一条的格式：**联动点 → 涉及文件 → 漂移后的症状 → 怎么改 → 怎么验证**。

---

## 1. 首屏骨架 ↔ 真实 Hero

**为什么存在两份**
`index.html` 里的 `<style id="hero-shell-style">` + `<div id="root">` 内的骨架，
用于消除 JS 加载期的白屏。它必须独立生效，所以不能依赖外部样式表，只能手写一份等价 CSS。

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `index.html` → `<style id="hero-shell-style">` | 骨架样式（手写 CSS） |
| `index.html` → `<div id="root">` 内的 `<section class="hero-shell">` | 骨架 DOM |
| `src/components/Hero.tsx` | 真实 Hero（React） |
| `src/index.css` → `@theme` 的 `--text-*` | 流体字号来源（骨架的 `clamp` 值抄自这里） |

**漂移后的症状**
首屏刷新时文字「跳一下」：位置、宽度或字号在 React 挂载瞬间变化。

**历史故障（实测数据）**
2026-09 修过一次：骨架 H1 写到 `y=104`、真实 Hero 在 `y=188`，挂载瞬间**下移 84px**；
副题块宽度从 1120px 收到 896px（**横向收窄 224px**）。原因是六处盒模型不一致：
内容缺 `max-w-4xl`、内边距写死、`min-height` 用 `62vh` 而非 `100svh - 4rem`、
H1 字号写死 `4.25rem` 而非 `clamp()`、字重写成 900（app 是 400）、
`justify-content` 与 app 的 `sm:justify-center` 不一致。

**当前约定（重要）**
骨架的**内容列 `.hero-col` 设为 `visibility: hidden`**，骨架只负责背景层与光斑。
原因：app 的首项位置 = `0.706 × 容器高度`，而容器高度 = `max(731px, 100svh - 4rem)`。
这是一个随视口高度连续变化的比例，骨架无法用与容器高度同源的度量复现它。已逐一验证并排除：

| 方案 | 实测偏差 |
| --- | --- |
| 固定 px | 640–1500px 视口高度区间内偏差 12–818px |
| 百分比 `padding` | 按**宽度**解析而非高度，偏出 900px 以上 |
| grid `fr` 轨道 | 单行自动放置时轨道塌陷，偏差 56–409px |
| `vh` / `svh` | 生产环境可响应，但无头仿真下不随视口变化，无法回归验证 |

所以**不要再尝试对齐骨架的文字位置**。骨架不渲染前景内容，就没有可错位的东西。

**怎么改**
- 只改 `Hero.tsx` 的视觉样式（颜色、圆角、图标）→ 无需动骨架
- 改 `Hero.tsx` 的**背景层**（光斑位置、网格）→ 同步改 `.hero-shell::before`
- 改首屏文案 → 同步改骨架 DOM（虽然不可见，但改掉更省心；文案也会影响 `subset-fonts` 的字符集）
- 想恢复骨架显示文字 → 必须同时满足：两处盒模型逐项一致 **且** 能接受垂直方向仍有偏差

**怎么验证**

```bash
npm run build && npx vite preview --port 5231
# 逐断点比较「骨架阶段」与「应用稳定后」的 H1 视口坐标
node <诊断脚本> http://localhost:5231/ 1440 900
```

判定标准：`x` 与宽度必须为 0 误差；CLS 必须为 0。

## 2. 首屏内联字体 ↔ 字体子集

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/fonts/*.woff2` | 子集化产物（唯一来源） |
| `scripts/subset-fonts.mjs` | 生成子集 |
| `scripts/inline-firstscreen-fonts.mjs` | 把柳建毛草 + 得意黑 base64 内联进 `index.html` |
| `index.html` → `<style id="font-face-inline">` | 内联产物（勿手改） |
| `vite.config.ts` → `FONT_FILES` | 构建后注入的 `<link rel="preload">` 列表 |

**漂移后的症状**
新增文案的用字不在子集内 → 回退到系统字体，粗细/字形与全站不一致。
或：`index.html` 内联的是旧字体，`src/fonts` 是新的，两者静默不同步。

**历史故障**
内联块原本是**人工粘贴**的、且内联的是子集化之前的旧文件，**没有任何生成器**。
文案变更后重跑子集化，`src/fonts` 更新而 `index.html` 不会。

**怎么改**
改完任何文案后：

```bash
npm run fonts:subset    # = subset-fonts.mjs + inline-firstscreen-fonts.mjs，两步必须成对
```

若新增了**首屏**展示层用字（H1、区块标题），还要看 `vite.config.ts` 的 `FONT_FILES`
是否需要把该字重加入预加载列表。

## 3. 主题初始化 ↔ 主题切换组件

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `index.html` → `<head>` 内联脚本 | 首屏前套用主题，避免闪白/闪黑 |
| `src/components/ThemeToggle.tsx` | 运行时切换 + 持久化 + 同步 `theme-color` |
| `index.html` → `meta[name="theme-color"]` × 2 | 移动端状态栏配色（带 media 查询） |

**漂移后的症状**
- 内联脚本与组件判定逻辑不一致 → 首屏闪一下再跳到正确主题
- `localStorage` 的键名或取值集合不一致 → 主题"记不住"
- 画布底色改了但 `theme-color` 没改 → 移动端地址栏与页面脱色

**已知的小瑕疵**
`theme-color` 的 media 查询针对 `prefers-color-scheme`，而 JS 会按**手动选择**覆写它。
两者可能不一致（手工选了深色、系统是浅色时）。目前不影响主流程，若要做移动端细节再收敛。

**怎么改**
三处的画布色值必须一致：`src/index.css` 的 `body` 背景、`index.html` 的 `theme-bg-inline`、
`ThemeToggle.tsx` 的 `m.setAttribute('content', ...)`。键名固定为 `localStorage.theme`，
取值集合固定为 `auto | light | dark`。

**另一处同类问题**
`ThemeToggle` 在移动端被渲染**两次**（`Navbar` 与 `MobileTabBar`），
各自持有独立 state，靠 `localStorage` 间接同步。目前表现正常，但这是隐患：
将来若把主题状态提升为共享 Context，两处都应改为消费同一个状态。

## 4. 色板 ↔ 组件里硬编码的颜色

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `src/index.css` → `@theme` | 色板唯一来源 |
| 各组件里的 `rgb(...)` / `#hex` 内联 | 装饰性渐变、光晕、SVG 描边 |

**漂移后的症状**
改了色板，但某些渐变/光晕仍是旧色，页面出现两种色系。

**当前已知的硬编码位置**（改色板时逐个检查）

| 位置 | 内容 |
| --- | --- |
| `About.tsx` 多定位卡背景 | `radial-gradient(... rgb(20 184 166 / .18) ... rgb(8 145 178 / .14))` |
| `BackToTop.tsx` 进度环渐变 | `<stop stopColor="#0d9488">` / `"#22d3ee"` |
| `BackToTop.tsx` 阴影 | `rgba(15,87,79,0.28)` |
| `SideDotsNav.tsx` 管体与节点 | `rgba(15,87,79,...)` 系列、`bg-cyan-200`、`rgba(103,232,249,...)` |
| `Hero.tsx` 头像 ring | 走 `ring-brand-100`，已是 token ✓ |

建议做法：把这类装饰色收敛为 `index.css` 里的 `--glow-*` 变量，组件引用变量而非字面量。

## 5. 响应式断点：JS 与 CSS 各写一份

**涉及文件**

| 文件 | 断点 |
| --- | --- |
| `src/hooks/useIsMobile.ts` | `(max-width: 639px)` |
| `src/components/Experience.tsx` | `sm:hidden`（640px 起隐藏） |
| `src/components/Hero.tsx` | `sm:hidden` / `hidden sm:block` |
| Tailwind 默认 | `sm = 640px` |
| `src/index.css` 的 `section-*` / `hero-inner` | `@media (min-width: 640px)` |

**漂移后的症状**
640px 附近出现「JS 认为是手机、CSS 认为是桌面」的错配：折叠按钮与布局状态对不上。

**当前状态**
`useIsMobile` 用 `max-width: 639px`，与 Tailwind 的 `sm:hidden`（`min-width: 640px` 才隐藏）
**恰好互补，无缝隙**。改动任一处时保持这个互补关系。

**建议**
能不靠 JS 判断的就不靠：优先用 `hidden sm:block` 这类纯 CSS 方案。
`Experience` 的「移动端默认折叠要点」因为需要交互状态才用了 JS，属合理例外。

## 6. 滚动侦测触发线 ↔ 锚点停靠位

**涉及文件**

| 文件 | 值 |
| --- | --- |
| `src/hooks/useScrollSpy.ts` | `TRIGGER_LINE = 128`（px） |
| 各 `section` 的类名 | `scroll-mt-16`（= 4rem = 64px） |

**漂移后的症状**
点击导航跳到某段后，右侧高亮的却是别的段；或滚动时高亮切换时机感觉"慢一拍"。

**当前状态**
两者是**不同的量**，并非笔误：`scroll-mt-16` 决定锚点跳转后板块顶部停在离视口顶 64px 处，
而 `TRIGGER_LINE = 128` 是"认为这一屏正在读这一段"的判定线。
但因为 128 > 64，锚点跳转完成后板块顶部位于 64px、还没越过 128px 的判定线，
所以**点击跳转后高亮可能仍停留在上一段**，直到继续滚动。这是一处真实的体验瑕疵，建议对齐（例如都取 96px）。

## 7. 数据库 ↔ JSON 数据源

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `database/portfolio.db` | 内容源（README 声明） |
| `src/data/*.json` | 构建数据 |
| `scripts/seed-db.mjs` | JSON → DB |
| `scripts/export-db.mjs` | DB → JSON（`npm run build` 自动执行） |

**漂移后的症状**
直接改了 `src/data/*.json` 但没跑 `db:seed` → 下次 `build` 时 `db:export` 用数据库覆盖你的修改。

**怎么改**
两条路选一条，不要混：

- 改 JSON → `npm run db:seed`
- 改 DB → `npm run db:export`

`npm run build` 含 `db:export`，所以**数据库始终是最终赢家**。

## 8. 预览页注入 ↔ 预览产物

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `scripts/polish-previews.mjs` | 注入演示提示条 + iframe 防护（幂等） |
| `public/preview/<id>/index.html` | 注入目标 |

**漂移后的症状**
重新构建复制预览产物进 `public/preview/` 后，注入内容被覆盖，演示提示与 iframe 防护消失。

**注意**
`polish-previews.mjs` 的 iframe 防护包含**两个元素**（CSP meta + frame-busting script），
清理时必须分别擦除，只擦 script 会让 meta 在每次重跑时累积。

**怎么改**
预览产物更新后重跑：

```bash
npm run previews:polish
```

## 9. 简历 PDF ↔ 归档原件

**涉及文件**

| 文件 | 角色 |
| --- | --- |
| `_archive/resumes/蒋宇龙简历.pdf` | 水印脚本的**输入**（归档原件） |
| `public/resume.pdf` | 水印产物（站点下载的文件） |
| `scripts/watermark_resume.py` | 生成器 |

**漂移后的症状**
直接编辑 `public/resume.pdf` → 下次重跑水印脚本会被归档原件覆盖。

**怎么改**
换简历时：先把新版放进 `_archive/resumes/`，再运行

```bash
npm run resume:watermark
```

脚本会自检文本层可提取性与页数，并打印结果。文本层是 ATS 解析依赖，**必须保留**。

## 附：新增联动点时的约定

1. **能一处定义就不要两处。** 优先用 CSS 变量、Tailwind token、或从单一数据源派生。
2. **无法避免的重复，必须在两处都写明注释**：指出「与谁联动」「漂移后的症状」「怎么验证」。
3. **加进本文档。** 每条至少写清涉及文件与验证方法。
4. **可验证的联动优先做成脚本。** 例如字体子集→内联已经做成 `npm run fonts:subset` 一步完成；
   联系方式、简历水印、预览注入同理。脚本比注释更可靠。
